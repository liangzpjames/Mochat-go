# Phase 3.2 八页功能对标实施计划

> **执行要求：** 必须使用 `subagent-driven-development`（推荐）或 `executing-plans` 按任务逐项执行；所有步骤使用复选框追踪，未通过当前任务验收不得进入下一页。

**目标：** 在 Phase 3.2 固定的八个页面中，为圆弧参考功能建立明确对应并完成真实业务闭环，同时形成统一、优雅且可维护的 Dashboard 视觉系统。

**架构：** 以 `manifest.json` 和功能矩阵共同管理完成度；每个页面沿“参考功能 → React 页面与 adapter → Go 服务和持久层 → 权限 → 自动化测试 → 浏览器证据”纵向交付。共享视觉由 Dashboard token 和页面壳组件统一，页面不直接拼装旧接口响应，也不依赖生产 fixture。

**技术栈：** Go 1.26、MySQL/MariaDB、React 19、TypeScript、Ant Design、TanStack Query、Vitest、Playwright、pnpm、Docker Compose。

## 全局约束

- Phase 3.2 仅包含 `/index`、`/chat/v2-all`、`/ai-insight/v2/sensitive-word`、`/customer/clue/default`、`/customer/contact`、`/customer/opportunity`、`/customer/public-sea`、`/customer/tags`。
- 每项参考功能只能标记为 `已对应`、`合理合并` 或 `不适用`；后两者必须记录原因、替代入口和验证方法。
- 完成页面不得引用 `DemoPage`、`PlaceholderPage` 或 `demo-fixtures`。
- 控件存在不等于功能完成；查询必须返回真实数据，命令必须真实持久化并可在刷新后读取。
- 服务端从认证上下文解析 tenant、corp 和数据权限范围，不信任客户端提交的范围。
- 列表、详情、导出和写操作必须使用相同的数据权限范围。
- 可变资源使用乐观版本；可重试写操作使用稳定幂等键。
- `403` 表示无权限，`404` 表示不存在或隐藏，`409` 表示版本冲突，`422` 表示非法状态流转。
- 视觉目标是统一、清晰、优雅，不要求与圆弧像素级一致。
- 自动化测试不得发送真实客户消息，不得触发破坏性第三方操作。
- 每个任务必须经过 RED、GREEN、集成验证、浏览器验证和独立提交。

## 执行顺序与停止条件

执行顺序固定为 Task 1 → Task 2 → Task 3～10 → Task 11。Task 3～10 可以按页面并行审计，但共享 SCRM 文件的实现必须串行合并。

出现以下任一情况立即停止当前页面的完成标记并修复：

- 圆弧原子功能未进入矩阵；
- MoChat 入口没有真实 API 或业务结果；
- 权限只能由前端隐藏控制；
- 写操作刷新后丢失；
- 浏览器证据与自动化测试不一致；
- 页面为追求相似外观而引入独立视觉规则；
- 全量门禁依赖手工修改 manifest 才能通过。
