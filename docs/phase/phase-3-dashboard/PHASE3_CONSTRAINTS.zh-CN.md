# Phase 3 Dashboard 主要约束

日期：2026-07-31

适用范围：Phase 3.2、Phase 3.3、Phase 3.4、Phase 3.5、Phase 3.6 和 Phase 3 Final。

## 1. 最终目标

Phase 3 最终必须把 `web/apps/dashboard/src/benchmark/manifest.json` 登记的 53 个页面全部升级为真实可用页面。

Phase 3 Final 必须满足：

- `placeholder` 页面数为 0；
- `demo` 页面数为 0；
- 生产路径不引用 `demo-fixtures`；
- 每个页面至少具有一条真实查询或命令主流程；
- 每个写页面具备真实持久化、权限、审计和异常处理；
- 53 个页面全部有自动化验收和仓库内可追溯证据。

“菜单可见”“路由可达”“页面样式完成”“接口已存在”或“fixture 可以演示”均不等同于功能完成。

## 2. 分阶段交付

Phase 3 按业务域纵向闭环，不按页面数量平均分批：

| 阶段 | 业务目标 |
| --- | --- |
| Phase 3.2 | Dashboard 基础、数据概览、全局消息、敏感词和 SCRM 核心链路 |
| Phase 3.3 | 会话与风险预警 |
| Phase 3.4 | 营销工具 |
| Phase 3.5 | SCRM 扩展与数据报表 |
| Phase 3.6 | AI 能力与企业设置 |
| Phase 3 Final | 53 项清零、全量回归和发布证据 |

每个阶段必须能独立构建、测试、部署和验收。未进入当前阶段的页面可以保留原状态，但不得被标记为当前阶段已完成。

## 3. 标准实施流程 v2

后续每个阶段和业务批次统一执行：

1. **范围冻结**：从 53 项 manifest 中选定页面，记录阶段内和阶段外范围。
2. **页面档案**：记录字段、状态、交互、权限和已观察行为，不猜测未观察行为。
3. **旧能力复用审计**：逐页映射旧路由、API、handler、store、数据表和测试。
4. **领域与 API 契约**：固定模型、状态机、错误码、分页、权限、幂等、版本和审计规则。
5. **失败测试基线**：先建立 Go、数据库、HTTP、React 和浏览器失败测试。
6. **纵向闭环实现**：按 migration、repository、service、handler、API adapter 和页面完成闭环。
7. **真实数据验收**：执行真实创建或修改，刷新后重新查询并验证结果。
8. **隔离与权限验收**：使用双租户、双企业和多角色验证。
9. **性能与异常验收**：覆盖执行计划、分页、并发、冲突、重试和部分失败。
10. **阶段门禁**：统一执行合同、类型、单元、集成、构建、E2E、视觉和证据检查。
11. **Manifest 升级**：全部门禁通过后才能提升实现和验收状态。
12. **阶段报告**：记录提交、命令、结果、证据和遗留风险。

不得跳过步骤 3、4、5、7 或 8，仅凭页面实现直接进入阶段完成验收。

## 4. Manifest 与完成状态

Manifest 是菜单、路由、实施阶段和完成度的唯一事实来源。每个页面至少记录：

- `domain`；
- `implementation`：`placeholder`、`demo`、`legacy-adapter`、`native`；
- `backend`：`missing`、`partial`、`ready`；
- `acceptance`：`not-started`、`unit-passed`、`integration-passed`、`e2e-passed`；
- `phase`；
- `owner`；
- `risk`；
- `legacyRoutes`；
- `evidence`。

完成页只能使用：

- `native`：使用正式领域 API 的真实实现；
- `legacy-adapter`：复用旧能力，但由明确 adapter 提供稳定的新页面合同。

`documented` 只能表示已登记，不能作为功能完成状态。检查器必须拒绝：

- 完成页仍使用 `DemoPage`、`PlaceholderPage` 或生产 fixture；
- `backend != ready` 却标记为 E2E 通过；
- 缺少页面证据却标记为阶段完成；
- Phase 3 Final 仍存在 `placeholder` 或 `demo`。

## 5. 架构与复用

- 保留 Phase 3.1 的 Dashboard shell、会话隔离、权限菜单和 page registry。
- 每个业务域建立独立 feature module，不建立包含全部菜单逻辑的超大页面文件。
- 前端通过 feature API adapter 访问后端，不直接拼接多套旧响应。
- 已有能力先审计再决定直接复用、adapter、扩展或替换，不重复创建同义 API。
- 新业务领域遵守 domain、application、ports、adapters 和 transport 边界。
- Dashboard 运行时不得读取 `docs`。
- 旧 URL 只有在存在真实部署入口或历史链接需求时才提供兼容，不为保留旧界面维护双套产品。

## 6. 数据与迁移

- 所有业务数据包含明确 `tenant_id`。
- 企业级资源包含 `corp_id`。
- 新 migration 必须从仓库当前最新编号顺延，不得复用、重编号或改写已发布 migration。
- 当前 `0099` 已被 `0099_saas_tenant_default_corp` 占用，SCRM 客户生命周期不得使用原计划中的 `0099`。
- Migration 必须有 up/down、checksum、apply、rollback、replay 和重复 apply 验证。
- 可变资源使用整数版本或等价的并发控制。
- 可重试命令使用稳定幂等键。
- 不可变事件只能追加，不允许覆盖历史。
- 公海领取、配额扣减和类似竞争操作必须使用真实数据库并发测试。

## 7. 权限与安全

服务端从认证上下文解析租户、当前企业和数据范围，不信任客户端提交的租户、企业、负责人或权限范围。

数据范围至少支持：

- 本人；
- 协作人；
- 本部门；
- 下级部门；
- 全企业；
- 明确授权的平台管理范围。

错误语义：

- 无权访问：`403`；
- 不存在或为避免泄漏而隐藏：`404`；
- 版本冲突：`409`；
- 非法状态流转：`422`；
- 参数无效：`400`。

写操作必须记录操作者、动作、目标、结果和时间。不得在日志、测试证据、截图或文档中提交访问令牌和未脱敏客户数据。

## 8. 页面与交互

所有真实页面按适用场景覆盖：

- 首次加载；
- 空数据；
- 筛选无结果；
- 403；
- 404；
- 409；
- 422；
- 网络或服务异常；
- 可重试错误；
- 重复提交；
- 异步任务进行中、失败和恢复；
- 登录失效。

列表筛选、分页和关键视图状态写入 URL。写操作成功后只失效相关缓存，不执行无边界的全局刷新。

固定 `1440x1000` 为桌面视觉验收基线。移动端至少保证可访问、无白屏和无破坏性溢出。

## 9. 测试与门禁

每个真实业务批次必须包含：

1. 领域和 application 单元测试；
2. repository 合同测试；
3. MariaDB 集成测试；
4. HTTP handler 合同测试；
5. React API adapter 测试；
6. React 页面交互测试；
7. Playwright 真实主流程；
8. 双租户、双企业和多角色隔离测试；
9. 适用的并发与幂等测试；
10. 大表查询的执行计划或性能证据；
11. 类型检查、lint、生产构建和架构边界检查；
12. 页面档案、截图和阶段报告完整性检查。

浏览器测试必须验证业务结果，而不是只验证按钮存在：

```text
登录
→ 进入页面
→ 查询或写入
→ 验证反馈
→ 刷新
→ 再次查询并验证持久化
→ 更换租户、企业或角色验证隔离
```

自动化环境不得发送真实客户消息、执行真实群发、购买或触发破坏性第三方操作。

## 10. 外部系统与异步任务

- 外部服务通过 provider 接口隔离。
- 测试 provider 与生产 provider 明确分离。
- 外部命令必须有幂等、超时、重试、取消或终止语义。
- 耗时导出、同步、群发和 AI 分析进入任务中心，不阻塞页面请求。
- 真实环境联调证据与自动化测试证据分开保存。
- 测试环境必须有防误发门禁。

## 11. AI 功能约束

AI 页面只有在接入真实模型或正式规则引擎并产生可追溯结果后才能完成。必须记录：

- 输入数据和权限范围；
- 模型、规则或知识库版本；
- 结果来源和生成时间；
- 失败、超时和降级；
- 隐私与审计；
- 调用额度或成本；
- 人工反馈或纠正入口。

静态文本、fixture 或无来源的随机结果不得标记为真实 AI 功能。

## 12. 文档与报告

每个阶段使用独立目录：

```text
docs/phase/<phase-name>/
  design/
  plans/
  acceptance/
  reports/
  evidence/
```

任务报告使用阶段和业务名称，不使用可能跨阶段冲突的通用 `task-N-report.md`。设计、计划、合同、验收命令、结果和遗留风险必须能从仓库独立理解，不依赖对话历史。

## 13. 阶段完成与 Phase 3 Final

阶段完成必须同时满足：

- 阶段内页面全部达到声明的真实实现状态；
- 阶段内核心业务可真实操作并持久化；
- 权限、隔离、异常、并发和性能门禁通过；
- Manifest、页面档案和验收证据同步更新；
- 没有未说明的失败测试或跳过项。

Phase 3 Final 额外要求：

- 53 个页面全部为 `native` 或经审查批准的 `legacy-adapter`；
- 全量菜单、直接 URL、刷新、前进后退和会话恢复正常；
- 每个业务域至少有一条跨页面真实 E2E；
- 全量回归、发布证据和风险清单完成；
- 不存在用视觉相似、路由可达或接口存在替代真实功能验收的情况。
