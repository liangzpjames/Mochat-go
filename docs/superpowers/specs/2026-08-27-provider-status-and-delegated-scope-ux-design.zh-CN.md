# Provider 状态与第三方能力范围体验设计

## 目标

本次调整只改变运营界面的信息层级和第三方授权范围的录入方式，不改变 Provider 状态事实来源、租户隔离、凭据保存方式或既有授权。

## Dashboard：唯一企业资料

### Provider 状态

继续读取 `/providers/status`，但页面只展示业务用户真正需要判断的三项信息：服务名称、当前状态、下一步。状态统一为“运行正常”“需要完善”“暂不可用”，不展示 Provider、source、code、环境变量、原始 capability、诊断时间和内部错误码。

服务名称使用中文业务语义：企业微信、会话存档、文件与录音、智能分析。下一步使用受控中文文案，不透传后端技术 action/reason，防止环境变量名或实现细节泄露到普通运营界面。

加载、无数据、无权限和状态源不可用仍然保持真实区分，并提供重试；文案不使用 Provider 等开发术语。

### 第三方代开发模式

唯一企业资料仍展示权威企业身份及当前对接模式。若模式为 `third_party_delegated`，Dashboard 不渲染任何“企微对接”配置或占位卡，也不请求自建应用专属的回调、同步状态接口。企业配置审计继续展示。

## SaaS：第三方能力范围

内部合同目前使用两个公开范围：

- `archive.read`：会话内容与媒体归档；
- `contacts.read`：通讯录与客户资料读取。

界面以中文多选项维护，不允许操作员输入内部 scope 字符串。首次配置或服务端尚无范围时默认全选；编辑已有配置时严格按已保存范围回显，避免把历史部分授权静默扩大。提供“全部开启”快捷操作，并至少保留一项能力的前端校验。

保存时才把中文选项转换为稳定 scope code；摘要显示“全部能力已开启”或“已开启 N 项”，并列出中文能力名，不显示内部标识。未知历史 scope 不丢弃：编辑和保存时保留未知值，但界面不将其冒充成当前支持能力。

## 安全与兼容性

- 永久授权码继续只写不读，关闭、失败和保存后清空。
- 不修改后端授权判定和 archive 的失败关闭条件。
- 不扩大已有租户的授权；仅新配置默认全开。
- 不新增数据库迁移或远端调用。
- 组件测试覆盖信息隐藏、第三方模式隐藏、默认全选、已有部分授权回显和保存 payload。

## 验收标准

1. Dashboard 不再出现 Provider、source、code、环境变量名、内部 capability 或诊断时间。
2. 第三方模式的唯一企业资料中不存在“企微对接”配置卡。
3. SaaS 第三方配置无自由文本能力范围输入，首次打开两项能力均已勾选。
4. 保存 payload 含全部默认 scope；已有部分范围不会在打开弹窗时自动扩展。
5. Docker 重建后在真实本地路由完成桌面点击、刷新、网络与控制台检查。
