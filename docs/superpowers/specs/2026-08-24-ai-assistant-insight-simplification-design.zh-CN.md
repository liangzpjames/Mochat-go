# AI 分析助手与洞察工作台精简设计

## 1. 背景与目标

当前 `/ai-setting/agent` 已限制为一个系统级“会话分析助手”，但页面仍沿用面向大量记录的指标、筛选、表格和分页结构，和实际只有一个助手的产品事实不匹配。`/ai-insight/smart-analysis` 又提供独立的规则新增、编辑、启停和删除入口，导致“设置”和“结果”职责重复，且用户可以创建没有独立业务入口的规则。

本次目标是：

1. 将“智能体管理”收敛为一个固定分析助手的轻量设置页，不开放新增、删除、改名和无业务入口的智能体。
2. 让同一个“会话分析助手”同时服务会话分析与智能分析；知识库、分析要求和唯一默认智能分析规则都在此处配置。
3. 将智能分析页收敛为结果查询、结果详情与会话跳转工作台，不再配置规则。
4. 统一 AI 洞察页面查询区按钮尺寸和层级，修复刷新按钮与查询、重置按钮不一致的问题。
5. 保持真实 Provider、会话存档、租户、企业、权限和持久化边界；Phase 7 继续暂停。

## 2. 现状范围与真实数据矩阵

| 页面/能力 | 路由 | 前端来源 | API | 后端/存储 | 本次处理 |
|---|---|---|---|---|---|
| 分析助手设置 | `/ai-setting/agent` | `AgentPage` | `GET/PUT /dashboard/ai-settings/agents` | `mochat_go_ai_agents`、知识库关联 | 精简为单卡片和单编辑弹窗 |
| 默认智能分析规则 | 原位于智能分析页 | `SmartAnalysisPage` | 原 `/dashboard/ai-insight/smart-analysis/rules*` | `mochat_go_ai_analysis_rules` 与不可变版本表 | 迁入分析助手设置，并固化为每企业唯一系统规则 |
| 智能分析结果 | `/ai-insight/smart-analysis` | `SmartAnalysisPage` | records/detail/status | 洞察结果、运行记录、来源消息 | 只保留查询、结果、详情、会话跳转 |
| 会话分析结果 | `/ai-insight/session-analysis` | `SessionAnalysisPage` | records/detail/status/export | 洞察结果、运行记录、来源消息 | 显示同一助手关联信息，保留现有结果能力 |
| 知识库 | `/ai-setting/ai-knowledge-base` | `KnowledgeBasePage` | 知识库与文档接口 | 私有文档、解析分段、知识库 | 不改业务范围；继续由助手关联并进入真实提示词 |
| 菜单与权限 | Dashboard 菜单 | manifest/catalog | 页面和 API 资源 | 权限资源表 | “智能体管理”改名“分析助手”；移除规则新增/删除/独立启停资源 |

所有结果字段继续来自后端结果快照，不增加前端业务假数据。Provider 未就绪、助手停用、知识库不可用或没有符合条件的存档消息时，页面展示真实运行状态或空态，不伪造成功结果。

## 3. 圆弧 AI 实测调研

2026-08-24 使用已登录界面实际点击以下路由：

- `/#/ai-setting/agent`
- `/#/ai-insight/smart-analysis`
- `/#/ai-insight/session-analysis`

### 3.1 可借鉴部分

- 智能体入口以少量固定卡片表达，而不是通用后台列表。
- “会话分析助手”详情集中管理最少消息数、无效沟通、分析周期、分析频率、免分析对象、手动触发和最大会话条数等规则。
- 智能分析页只有查询、刷新、结果表格、分页和详情，不在结果页新增规则。
- 会话分析结果在列表直接展示成交意愿、流失风险和摘要；详情以客户分析、员工质检、证据维度、关键词、需求、情绪、话术与动作建议分层。
- 结果与原会话分开查看，避免把设置、原文和结果塞在同一层级。

### 3.2 不照搬部分

- 圆弧智能体页在当前宽屏出现水平溢出，首张卡片被截断；MoChat 使用自适应单卡片，不复制该布局问题。
- 圆弧助手详情是接近全屏的大表格，规则密度过高；MoChat 只暴露当前真实执行链已支持的分析要求、会话范围、回看天数、最少消息数、知识库和总开关。
- 圆弧智能分析空态占用大面积且刷新按钮游离；MoChat 将刷新放入统一查询操作区，并保持按钮等高。
- 圆弧详情虽然信息丰富，但部分得分口径由其产品定义；MoChat 只展示本系统 Provider 返回且通过 Schema/证据 ID 校验的字段。

## 4. 方案比较与选择

### 方案 A：继续保留多规则，只移动前端入口

改动最小，但隐藏 API 仍可创建无入口规则，Runner 仍会执行多条规则，不能满足“所有智能分析都用这个规则”。不采用。

### 方案 B：增加第二个“智能分析助手”

业务边界直观，但需要再维护一套助手状态、知识库和 Provider 上下文；当前两个分析页面共享同一会话事实和知识背景，分成两个助手会增加配置冲突。暂不采用。

### 方案 C：一个固定分析助手 + 一个固定智能分析规则（采用）

保留一个“会话分析助手”，明确它是 AI 洞察唯一入口；助手基础设置用于会话分析和智能分析，内嵌一个不可新增、不可删除、不可改名的“默认智能分析规则”。保存时在同一数据库事务更新助手、规则和规则版本。Runner 只读取该系统规则，并将助手要求、知识库和状态同时应用到两类分析。

该方案最符合当前只有一个真实业务入口的事实，也为未来出现第二个明确业务场景时保留通过新的 `system_key` 扩展固定助手的能力。

## 5. 信息架构与交互

### 5.1 菜单关系

- `AI 洞察`：消费层，只看会话分析、智能分析及其详情/来源会话。
- `AI 设置`：生产配置层，包含 `AI 知识库` 与 `分析助手`。
- 原菜单名“智能体管理”改为“分析助手”，路由保持 `/ai-setting/agent`，避免破坏既有收藏、权限路径和深链。

### 5.2 分析助手页

页面不再显示 KPI、关键词、状态筛选、表格、分页和新增入口。主体为一个自适应助手卡片：

- 名称、系统助手标识、启停状态、最后更新时间。
- 明确列出“用于会话分析 / 用于智能分析”，可跳往两个结果页。
- 显示关联知识库数量、可用文档数量、默认规则版本和规则摘要。
- 只有“编辑配置”和统一“刷新”两个主要操作；刷新与编辑按钮高度一致。

编辑弹窗包含三个清晰分区：

1. 助手要求：固定名称、分析要求、总运行状态。
2. 知识库：关联已启用知识库，保留对已停用/失效既有关联的诚实处理。
3. 默认智能分析规则：固定规则名称、分析目标、客户单聊/客户群聊、回看天数（1–30）、最少消息数（2–50）。

保存为单次 PUT；失败时不关闭弹窗，展示机器码映射后的具体错误。脏数据关闭仍提供放弃确认；Escape、遮罩和关闭按钮遵守现有 DashboardDialog 契约。

### 5.3 智能分析页

- 删除“分析结果 / 分析规则”页签、规则新增按钮、规则列表和规则编辑抽屉。
- 删除“规则版本”查询输入；历史结果仍在表格和详情展示规则快照/版本，保证审计可追溯。
- 顶部显示“由会话分析助手生成”的紧凑关联条，状态、知识库和文档数量来自 status API，并提供“前往配置”。
- 保留关键词、会话类型、开始/结束日期、查询、重置、刷新、结果表、分页、结果详情和“查看原会话”。
- 查询、重置、刷新统一 `min-height: 36px`、边框、圆角和内边距；窄屏下操作区换行但不改变按钮高度。

### 5.4 结果展示原则

- 列表用于快速判断：对象、默认规则版本、结论、状态、来源窗口、分析时间。
- 详情用于复核：结论、匹配/置信度、建议、来源消息证据和会话跳转。
- 会话分析继续展示更丰富的客户/员工结构化结果；本次不重写其 Schema。
- 失败结果展示后端 `errorSummary`/运行状态，不把失败显示为零结果。

## 6. 数据模型、迁移与执行链

新增迁移 `0158_ai_assistant_default_smart_rule`：

1. 为 `mochat_go_ai_analysis_rules` 增加可空 `system_key`，建立 `(tenant_id, corp_id, system_key)` 唯一索引。
2. 为每个有效租户/企业写入 `system_key='default-smart-analysis'` 的唯一规则及 v1 版本；已有自定义规则保留用于历史审计，但不再被 Runner 选取。
3. 将页面显示名从“智能体管理”更新为“分析助手”。
4. 删除智能分析权限下规则 POST、PUT、DELETE、独立状态接口资源；HTTP Handler 对这些旧写入口返回 405，防止绕过 UI 创建无入口规则。

`GET /dashboard/ai-settings/agents` 返回唯一助手及 `smartAnalysisRule`。`PUT /dashboard/ai-settings/agents/{id}` 在一个事务内：

- 锁定并更新系统助手；
- 锁定并更新系统默认规则；
- 仅在规则字段变化时递增版本并写入不可变版本表；
- 写入设置审计；
- 任一步失败则整体回滚。

Runner 只读取系统默认规则的当前版本。助手停用、加载失败或 Provider 未就绪时，会话分析和智能分析都记录真实失败运行；助手启用时，两类分析共享助手要求、知识库检索上下文和设置指纹。规则版本、来源消息指纹和助手设置指纹共同保证刷新后的持久化与可追溯重跑。

## 7. 权限、租户与安全边界

- 所有助手、规则、规则版本、知识库、结果和运行查询必须同时限定 `tenant_id` 与 `corp_id`。
- 页面仍由 `dashboard.ai_setting.agent`、`dashboard.ai_insight.session_analysis`、`dashboard.ai_insight.smart_analysis` 分别授权；设置页不要求用户同时拥有洞察页权限。
- 固定助手只能 PUT，不支持 POST/DELETE；系统规则不支持独立写接口。
- 知识库文档继续使用私有存储和已验证解析链，不通过公共静态目录暴露。
- 知识库内容只作为低优先级背景，不能成为证据 ID，也不能覆盖系统约束、来源会话和 JSON Schema。
- 不接入新的外部 Provider，不扩大企微会话存档范围，不恢复 Phase 7。

## 8. 响应式与视觉原则

- 继承已验收 Dashboard 的导航、顶栏、卡片、弹窗、反馈和宽屏间距。
- 2560×1440 时助手卡片使用可读最大宽度但不出现横向滚动；常规桌面充分利用内容区。
- 700px 以下卡片信息、规则字段和操作按钮单列；390×680 下弹窗只滚动内容区，底部操作可达。
- 小高度下弹窗不溢出视口；表格横向滚动限定在结果容器内。
- 所有查询操作按钮高度统一；hover 不使用位移或滤镜导致文字模糊。

## 9. 验收标准

1. 分析助手页只显示一个固定助手，无新增、删除、筛选、分页和通用管理表格。
2. 用户能一次保存助手要求、知识库、状态和唯一默认智能分析规则；刷新后配置与版本持久化。
3. 智能分析页没有任何规则配置入口，只显示真实结果、运行状态、详情和会话跳转。
4. Runner 只执行系统默认规则，并将助手状态、要求、知识库和指纹用于两类洞察。
5. 旧规则写接口返回 405；跨租户/跨企业更新失败；规则版本和审计可追溯。
6. 刷新、查询、重置、编辑按钮在真实浏览器中等高，常规桌面、2560×1440、390×680 和小高度无异常溢出。
7. Provider 未就绪、无存档消息、无结果、加载失败和助手停用均有诚实状态，不出现假成功或假数据。
8. 目标测试、Dashboard 全量测试、typecheck、目标 lint、production build、相关/全量 Go 测试、迁移/RBAC/benchmark/evidence 门禁和 `git diff --check` 通过；全量 lint 若仍有历史基线，按新鲜输出如实记录。

## 10. 回滚边界

- 前端可回滚到原页面组件，不影响已产生结果。
- 迁移 down 只移除系统默认规则、规则版本、唯一索引和 `system_key` 列，并恢复菜单名/权限资源；不删除历史自定义规则或洞察结果。
- 不删除 Docker 命名卷；运行时回滚只重建 app 并执行受控 down migration（如确有需要）。
