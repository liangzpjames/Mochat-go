# 超时预警与客户流失页面优化设计

> 文档日期：2026-08-21
>
> 审阅状态：已确认，实施中
>
> 目标路由：`/ai-insight/v2/timeout`、`/ai-insight/v2/customer-loss`

## 1. 目标与停止点

本轮优化“超时预警”和“客户流失”两个风险预警菜单页。页面借鉴圆弧 AI 的信息架构、视觉密度和操作节奏，但数据、状态、规则和操作必须来自 MoChat 的真实业务链路，不复制参考站的示例数据，不用动态英文键拼表格，也不展示不能闭环的按钮或说明卡。

本轮最终实施目标：

1. 两页采用统一的紧凑风险工作台，不再使用占据首屏的大块介绍卡；
2. 筛选、表格、分页、详情、批量处置、规则配置和设置形成完整交互闭环；
3. 超时预警接通归档消息后的自动等待、回复识别和规则评估，不再依赖人工调用评估接口；
4. 客户流失按企业微信真实删除事件生成历史快照，准确区分“员工删除客户”和“客户删除员工”；
5. 所有列表使用固定中文字段和类型化 API，查询条件、页码、标签页和抽屉选择可通过 URL 恢复；
6. 实施完成后通过单元测试、MariaDB 集成测试、Docker 构建和本地浏览器逐项验收。

产品呈现继续遵循“只展示可闭环能力”。页面不出现“能力未接入”“当前数据无法识别”一类说明，也不保留禁用占位入口。确实依赖独立供应链、不能在本轮页面优化内可靠完成的能力，只登记到 `docs/PROJECT_PROGRESS.zh-CN.md`。

用户已确认开始实施。本轮范围严格限定为两个风险预警菜单：`/ai-insight/v2/timeout` 与 `/ai-insight/v2/customer-loss`；客户会话菜单不属于本轮交付，也不因本设计产生任何会话页改动。无法仅靠页面完成的真实数据闭环继续登记到总进度文档，不在页面中展示能力缺口提示。

## 2. 已确认的参考与现状

### 2.1 圆弧 AI 参考页

2026-08-21 已在登录态下检查以下参考路由：

| 页面 | 参考路由 | 主要结构 |
|---|---|---|
| 超时预警 | `/#/ai-insight/v2/timeout` | “超时记录 / 规则配置 / 高级设置”三个标签；紧凑筛选栏；记录表格；批量审计；分页；规则列表与编辑；结束语、白名单消息类型双栏设置 |
| 客户流失 | `/#/ai-insight/v2/customer-loss` | “客户流失 / 客户流失配置”两个标签；紧凑筛选栏；流失记录表格；批量审计；分页；规则列表与编辑 |

参考页的关键表达原则是：标签紧贴内容、查询区不占用多余高度、单一主表格尽量填满页面、详情和配置通过独立操作层展开。MoChat 采用这些原则，但不照搬参考页的企业信息、风险数字、AI 摘要、H5 地址、字段名称或数据结果。

### 2.2 MoChat 当前超时预警

前端实现：`web/apps/dashboard/src/features/phase33/timeout-warning-page.tsx`。

当前问题：

- 顶部大块介绍卡重复展示标题和刷新按钮，占据首屏；
- 记录、规则和设置均由一个超长组件用 `Record<string, unknown>` 动态处理，类型和错误边界不清晰；
- 记录固定请求第 1 页，缺少真实分页、规则、处置状态和日期筛选；
- 表格使用 ID、原始状态值和简单按钮，批量处置没有统一确认与结果反馈；
- 规则编辑器只覆盖名称、会话范围和超时时长，监听对象、员工/部门选择、静音时段等真实后端能力没有完整呈现；
- 高级设置依赖手工输入逗号和分号，容易生成错误结构；
- `aiInsightEnabled` 被前端默认写成 `true`，但记录写入时 `ai_summary` 实际为 `NULL`；
- `notify_type` 只生成待发送 intent，仓库中没有通知分发器；
- 最重要的问题是：现有 `EvaluateTimeoutMessage` 只有内部 HTTP 评估入口，归档消息写入链路没有自动调用，不能形成真实、持续的超时记录生产闭环。

已有真实基础：

- `mochat_go_timeout_rules`、策略、静音时段、通知目标、设置、记录、审计和 intent 表已存在；
- 规则校验支持全员/员工/部门、单聊/群聊、1～5 条 3～180 分钟策略、风险等级和静音时段；
- 记录读取已按租户、企业和员工数据范围隔离；
- 批量确认、忽略、关闭和分派已有后端写入能力；
- 结束语词组和白名单消息类型已有真实设置存储；
- 会话存档同步已统一进入 `upsertWorkMessageArchiveWithExecutor`，可作为自动评估的可靠入口。

### 2.3 MoChat 当前客户流失

前端实现：`web/apps/dashboard/src/features/phase33/customer-loss-page.tsx`。

当前问题：

- 顶部同样使用大块介绍卡；
- 只有“员工 ID”文本框，缺少客户、流失类型、日期、处置状态和规则筛选；
- 根据第一行 `Object.keys` 动态生成英文表头，业务语义和列顺序不稳定；
- 请求固定第 1 页，没有分页控件；
- 详情直接遍历对象键值，没有结构化信息；
- 没有批量处置、导出、规则配置或历史快照；
- 当前 `/dashboard/workContact/lossContact` 直接读取 `mc_work_contact_employee status IN (2,3)`。关系重新添加时同一行会恢复为 `status=1` 并清空 `deleted_at`，因此旧流失事件会消失，不能作为长期审计记录。

已确认的真实状态和事件语义：

| 企业微信事件 | 本地状态 | 业务含义 |
|---|---:|---|
| `change_external_contact.del_external_contact` | `2` | 员工主动删除客户 |
| `change_external_contact.del_follow_user` | `3` | 客户删除员工，即被动流失 |

当前企微回调 worker 已处理这两个事件，并在同一事务中更新关系状态与 `deleted_at`。因此本轮可以建立真实的客户流失历史记录，不需要伪造风险数据。

## 3. 方案比较与结论

### 方案 A：只改 CSS 和表头

保留当前接口和组件，只压缩页头、翻译字段并增加分页样式。

- 优点：改动小；
- 缺点：超时记录仍不会自动产生，客户重新添加后历史仍消失，规则和批量处置仍不完整；页面看起来更像参考页，但业务闭环没有成立。

### 方案 B：建立一个通用“AI 风险引擎”承载两页

把超时和流失统一成抽象风险事件、通用规则和通用动作。

- 优点：模型表面统一；
- 缺点：两个领域的触发方式、设置和状态不同；会扩大到消息通知、AI 摘要和其他风险菜单，实施范围过大，容易破坏已有超时表和企微回调链路。

### 方案 C：共享视觉骨架、两个独立真实纵切面（采用）

两页共用紧凑标签、查询栏、工具栏、表格、分页、抽屉、状态徽标和 URL 状态规则；超时预警继续使用并补全现有 timeout provider，客户流失建立独立的事件快照和规则 provider。

采用原因：

- 视觉和交互能够保持一致；
- 不牺牲两个领域的真实数据语义；
- 可以在现有归档写入和企微回调事务上补齐生产链路；
- 后续其他风险页若需要，可复用视觉组件，但不会被迫进入同一个业务表。

## 4. 统一页面设计

### 4.1 页面骨架

1. 保留现有左侧菜单、菜单名称、顶部 banner 和路由；
2. 删除页面内部的大块介绍卡，内容区从标签页开始；
3. 标签页下方是单行紧凑查询区，字段过多时允许换成两行，但操作按钮始终靠右对齐；
4. 查询、重置、刷新和导出只出现一次，不在页头重复放刷新；
5. 主内容使用一张全宽数据卡，表头固定、表体滚动、分页固定在卡片底部；
6. 主按钮使用蓝色实心样式，次按钮使用白底描边，危险操作使用红色文字/描边并二次确认；
7. hover 只改变背景、边框和文字颜色，不使用位移或缩放；
8. 详情、规则编辑和批量处置使用右侧抽屉；支持关闭按钮、遮罩和 `Escape`；
9. 所有按钮提交中显示“处理中…”并禁用，成功后保持当前筛选和页码，失败后保留输入；
10. 表格不再根据数据动态生成列，不展示原始英文状态或 JSON。

### 4.2 宽屏与响应式

- `2560×1440`：内容使用全部主区域，不设置 `1320px` 最大宽度；查询区和表格尽量单行展示；
- `1440×900`：保留关键列，较长文本截断并用标题提示，表格允许水平滚动；
- `1024px` 以下：筛选区变成两列或单列；抽屉占满可用宽度；批量工具栏可换行；
- 主内容区高度使用 `min-height: 0` 和网格/弹性布局，避免整页被表格撑长；
- 页面只保留一个外层主滚动区，表格体和抽屉内容可独立滚动。

### 4.3 URL 状态

共同参数：

- `tab`：当前标签；
- `page`、`perPage`：当前页和每页条数；
- `recordId`、`ruleId`：当前打开的详情或规则；
- 各页筛选参数只在点击“查询”后写入 URL；草稿输入不触发请求；
- 切换标签时清除不属于该标签的页码、勾选项和抽屉；
- 修改筛选或每页条数时回到第 1 页；
- 刷新浏览器后恢复标签、筛选、页码和可恢复的详情；目标记录已不存在时关闭抽屉，不显示错误占位。

### 4.4 状态与空态

| 状态 | 页面行为 |
|---|---|
| 正在加载 | 表格骨架；保留查询条件 |
| 当前条件无记录 | 表格内业务空态，提示调整筛选或等待真实事件 |
| 没有任何规则 | 规则表空态并提供“新增规则” |
| 权限不足 | 权限空态，不渲染数据和写操作 |
| 接口失败 | 表格内错误状态与“重试” |
| 写操作失败 | 抽屉/工具栏内错误提示，保留选择和输入 |
| 记录资料已删除 | 使用历史快照名称和头像；不因当前资料不存在而隐藏记录 |

页面不渲染系统能力说明卡。供应链边界只进入总进度文档。

## 5. 超时预警页面

### 5.1 标签与记录页

标签保持：

1. `超时记录`
2. `规则配置`
3. `高级设置`

记录筛选：

- 客户名称或 ID；
- 风险等级：全部、低、中、高；
- 会话类型：全部、单聊、群聊；
- 风险规则；
- 处置状态：待处置、已确认、已忽略、已关闭；
- 记录日期起止；
- 查询、重置、刷新、导出。

记录表格固定列：

| 列 | 数据来源与展示 |
|---|---|
| 选择 | 当前页复选框；支持全选当前页 |
| 超时时长 | `timeoutSeconds` 格式化为“3 分 20 秒” |
| 触发消息 | `triggerMessage`；空文本按真实消息类型显示“[图片]”“[文件]”等 |
| 相关人 | 客户头像/名称 + 责任员工名称，不显示裸 ID |
| 会话类型 | `single=单聊`、`group=群聊` |
| 风险等级 | 低/中/高中文徽标 |
| 规则 | `ruleName`，历史规则删除后仍使用快照名 |
| 处置状态 | 待处置/已确认/已忽略/已关闭 |
| 记录时间 | `occurredAt` |
| 操作 | 详情 |

本轮不展示“AI 摘要”列。现有记录的 `ai_summary` 没有真实生成器，显示空列或模板文案都会误导用户。对应能力登记到总进度文档。

批量工具栏只在有勾选时出现，包含：

- `确认超时`
- `忽略记录`
- `关闭记录`
- `分派处理人`

批量处置统一打开抽屉填写备注；分派处理人使用员工选择器，不让用户输入员工 ID。提交前显示记录数量、动作和处理人，成功后清空勾选并刷新当前页；若当前页已空且页码大于 1，则回退一页。

详情抽屉展示触发消息、客户、责任员工、会话类型、超时时长、规则、风险等级、处置状态、当前分派、记录时间和审计轨迹。审计轨迹来自 `mochat_go_timeout_record_audits`，不通过前端猜测。

### 5.2 规则配置

规则列表筛选：规则名称、启用状态；操作：查询、重置、刷新、新增规则。

固定列：规则名称、监控对象、会话范围、超时策略、触发次数、启用状态、创建时间、操作。

规则抽屉：

- 规则名称；
- 监控对象：全部员工、指定员工、指定部门；
- 指定员工/部门使用名称选择器和已选标签，不输入裸 ID；
- 会话范围：单聊、群聊；
- 1～5 条策略，每条包含超时时长和风险等级；
- 静音时段：星期、开始时间、结束时间，最多 5 条；
- 启用状态；
- 保存、取消。

同一规则内超时时长不可重复，前端即时提示，后端继续做最终校验。删除规则前说明“只删除规则，不删除已产生的历史记录”。

本轮规则抽屉不展示 AI 开关和通知方式。AI 摘要没有生成器，通知 intent 没有分发器；继续展示会形成虚假配置。两项只在总进度文档登记，不出现在页面说明中。

### 5.3 高级设置

使用接近参考页的左右双栏：

- 左栏“结束语”：最多 5 个词组；每组最多 20 个词；支持新增/删除词组、标签输入、单词删除；
- 右栏“白名单消息类型”：以可选标签展示当前后端能识别的真实消息类型，例如图片、语音、视频、文件、链接；
- 底部统一“保存设置”，未修改时禁用；保存成功刷新当前设置；
- 不再用逗号、分号让用户手工编辑 JSON 结构。

### 5.4 自动预警数据链

超时预警必须从真实归档消息自动生产：

```text
会话存档写入
  ├─ 客户入站消息 → 写入/更新待评估消息
  └─ 员工出站消息 → 将同一会话更早的待评估消息标记为已回复
                         ↓
             周期任务扫描未回复且已达到时长的消息
                         ↓
        读取启用规则、结束语、白名单、静音时段和员工部门
                         ↓
              按策略生成超时记录（唯一键去重）
                         ↓
                 记录页查询、处置与审计
```

待评估消息保留到允许的最大超时时长 180 分钟；每次周期扫描都可命中已经达到的不同策略，记录表唯一键保证同一消息、规则、策略只生成一次。员工在时限内回复后不生成记录；在低风险策略后、高风险策略前回复，只保留已经真实触发的低风险记录。

单聊会话键使用“员工 + 客户”；群聊会话键使用群 ID，任一员工在群内回复都结束该群消息的继续等待。客户、员工、消息文本和时间在待评估时保存快照，资料后续删除不会破坏历史记录。

## 6. 客户流失页面

### 6.1 标签与记录页

标签：

1. `客户流失`
2. `流失规则`

记录筛选：

- 客户名称或 ID；
- 关联员工；
- 流失类型：员工删除客户、客户删除员工；
- 风险等级：未分级、低、中、高；
- 触发规则；
- 处置状态：待处置、已确认、已忽略、已关闭；
- 流失日期起止；
- 查询、重置、刷新、导出。

记录表格固定列：

| 列 | 数据来源与展示 |
|---|---|
| 选择 | 当前页复选框和全选当前页 |
| 流失类型 | `employee_removed_customer=员工删除客户`；`customer_removed_employee=客户删除员工` |
| 最近消息 | 流失发生前可追溯到的最后一条真实归档消息；没有则显示 `--` |
| 相关人 | 客户历史头像/名称 + 当时关联员工名称 |
| 风险等级 | 未匹配规则显示“未分级”，不伪造风险 |
| 触发规则 | 匹配规则的名称快照；未匹配显示“未匹配规则” |
| 处置状态 | 待处置/已确认/已忽略/已关闭 |
| 流失时间 | 企业微信删除事件时间或同步识别时间 |
| 操作 | 详情 |

详情抽屉展示客户、员工、流失类型、事件来源、最近消息、标签快照、规则、风险、处置状态、流失时间和审计轨迹。记录使用事件发生时快照；客户重新添加、改名或当前资料被删除后，历史详情仍稳定。

批量操作：确认流失、忽略记录、关闭记录。动作使用统一处置抽屉和备注，服务端按租户、企业、数据权限和记录 ID 校验，不接受客户端企业 ID。

### 6.2 流失规则

规则列表筛选：规则名称、启用状态；操作：查询、重置、刷新、新增规则。

固定列：规则名称、监控对象、流失类型、风险等级、触发次数、启用状态、创建时间、操作。

规则抽屉：

- 规则名称；
- 监控对象：全部员工、指定员工、指定部门；
- 流失类型：员工删除客户、客户删除员工，可多选；
- 风险等级：低、中、高；
- 启用状态；
- 保存、取消。

一个事件可能同时匹配多条规则。为保证记录不重复，服务端固定选择风险等级最高的规则；风险相同则选择 ID 最小的规则。触发次数只增加实际选中的规则。规则删除后历史记录保留名称和风险快照。

### 6.3 真实事件快照

客户流失记录由以下链路生产：

```text
企微删除回调 / 客户关系同步识别
            ↓
更新 mc_work_contact_employee 状态和 deleted_at
            ↓（同一事务）
读取客户、员工、部门、标签和最近归档消息
            ↓
匹配启用的流失规则；没有匹配则标记“未分级”
            ↓
写入不可变流失记录快照
            ↓
记录页查询、处置与审计
```

事件来源分为：

- `wecom_callback`：企业微信明确删除事件，精确度最高；
- `sync_reconcile`：关系同步确认记录已消失；
- `legacy_backfill`：迁移时从现有 `status IN (2,3)` 关系补入的历史记录。

员工离职时批量软删其关系不写客户流失记录，避免把员工离职误判为客户流失。历史回填中的 `status=2` 也必须排除已删除/离职员工关系；`status=3` 可按“客户删除员工”回填。

## 7. 数据与接口设计

### 7.1 超时预警接口扩展

## 8. 权限、安全与并发

- 认证身份、`tenant_id`、`corp_id` 和数据范围只来自请求上下文；忽略或拒绝客户端同名参数；
- 记录读取、详情、导出和批量处置都应用员工数据范围；规则和高级设置属于企业级配置，需要 `manage` 权限；
- 页面按 `read/manage/export` 能力隐藏无权按钮，不渲染点击后才报错的入口；
- 批量写入在事务内逐条验证企业和数据范围，返回实际更新数量；
- 规则编辑、状态切换和删除提交期间锁定对应行，防止重复点击；
- 归档消息和客户删除回调的记录生产必须幂等；重复队列投递不得增加触发次数；
- 所有自由文本做长度限制；CSV 做公式注入保护；详情不渲染原始 HTML；
- 规则删除、关闭记录等不可逆业务操作需要确认，但不删除原始事件和审计。

## 9. 明确不在页面展示的能力

以下能力本轮不显示入口、开关、列或说明卡，只在实施时登记到 `docs/PROJECT_PROGRESS.zh-CN.md`：

1. **AI 摘要生成**：当前 `ai_summary` 没有模型调用、任务状态、重试和成本治理链；
2. **超时通知发送**：当前只有 notification intent，没有企微/站内通知分发、重试和送达审计；
3. **客户流失预测**：本轮是对已发生删除事件的识别、分级和处置，不把历史行为包装成未发生流失的预测模型。

这些能力均需要独立的供应商、任务队列或模型评估专项，无法通过页面样式优化可靠补齐。除此之外，本设计列出的筛选、分页、规则、记录、处置、导出和真实触发链均纳入本轮实施。
