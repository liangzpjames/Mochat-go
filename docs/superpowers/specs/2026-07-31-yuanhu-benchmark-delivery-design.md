# 圆弧 AI 对标交付设计

日期：2026-07-31

## 1. 背景与目标

MoChat Go 需要以当前已登录的圆弧 AI 系统为产品、视觉和交互基准，逐步形成可演示并最终可实际使用的独立系统。

本设计采用两条验收线：

1. 菜单与全局框架先一次性达到视觉准确、路由可达、状态正常和可演示。
2. 业务页面按优先级逐个完成真实前端、后端、数据和权限闭环。

现有前端不构成兼容约束。能够达到目标效果的代码直接复用；仅业务逻辑可用的实现保留逻辑并重做视图；阻碍目标实现的页面或组件直接替换。最终验收关注与圆弧的视觉效果、操作行为和业务结果是否一致，不以旧界面保留率或代码复用率作为指标。

## 2. 范围与已知规模

当前圆弧 AI 基准系统包含以下八个菜单分组：

- 会话
- 风险预警
- AI 洞察
- 营销工具
- SCRM
- 数据报表
- AI 设置
- 企业设置

加上数据概览，当前已观测到约 56 个可点击页面入口。菜单数量和具体路由以版本化的基准清单为唯一事实来源，后续观测到增删时通过清单变更记录更新。

第一阶段覆盖全部菜单、全局布局和所有已登记路由。首批真实业务页面为：

- 数据概览
- 全局消息
- 敏感词

本设计不要求第一阶段完成全部页面的真实后端能力，也不把移动端像素级复刻纳入第一阶段强制范围。

## 3. 页面分级

所有页面必须登记为 P0、P1 或 P2，并允许按实施进度逐级升级。

### 3.1 P0：真实可用

P0 页面必须具备真实前端、Go API、权限、租户隔离、数据持久化、异常状态、自动化测试和视觉验收，能够完成目标业务闭环。

首批 P0 页面：

- 数据概览
- 全局消息
- 敏感词

### 3.2 P1：高保真演示

P1 页面复刻目标页面的主要布局、筛选、表格、按钮、弹窗或抽屉以及关键演示交互。数据来自独立、稳定的 fixture/mock 层，不得伪装成真实持久化能力。

首批 P1 页面：

- 员工会话
- 客户会话
- 群聊会话
- 风险行为
- 超时预警
- 会话分析
- 渠道活码
- 联系人
- 客户群

### 3.3 P2：准确框架

其余页面先提供准确的页面外框、标题和路由状态，并以统一的建设中内容承接。P2 页面不得出现白屏、404、错误路由或失效菜单。

P0、P1、P2 标识只在开发环境中显示，演示环境不显示内部实施等级。

## 4. 复用与替换决策

每个页面实施前必须完成一次复用评估：

| 现状 | 决策 |
| --- | --- |
| 视觉、交互和数据均匹配 | 原样复用 |
| 业务逻辑匹配，视觉不匹配 | 保留逻辑，重做视图 |
| 只有基础组件可用 | 拆出并复用基础组件 |
| 页面结构或交互与圆弧差异较大 | 直接替换 |
| 没有现有实现 | 全新开发 |

共享的 `auth`、`api-client` 和 `routing` 等基础设施在满足目标行为时优先保留。`dashboard` 的布局、页面结构和样式允许重构或替换。旧路由仅在部署入口或已知历史链接确有需要时提供重定向，不为保留旧界面维护双套页面。

## 5. 前端架构

### 5.1 基准清单

建立 `benchmark-manifest` 作为菜单和页面状态的唯一事实来源，至少记录：

- 菜单分组、名称、路由和图标
- 权限要求
- P0/P1/P2 等级
- 采集、设计、实现和验收状态
- 基准截图版本
- 页面档案位置

菜单、路由注册、完成度检查和导航测试均从该清单派生，禁止手工维护互相独立的重复清单。

### 5.2 全局框架

`dashboard-shell` 统一负责：

- 侧栏分组、展开、收起和当前路由高亮
- 顶部搜索入口
- 待接收线索、信息同步和任务中心入口
- 企业与用户信息
- 主内容区布局
- 刷新、前进、后退和直接访问路由时的状态恢复

所有业务页面共用该框架，不得复制全局布局。

### 5.3 页面注册

`page-registry` 根据基准清单把路由映射到三种实现：

- P0：真实业务模块
- P1：高保真演示模块
- P2：标准建设中页面

同一路由从 P2 升级到 P1、再升级到 P0 时，不改变菜单合同和路由身份。

### 5.4 共享视觉与业务组件

在现有共享 UI 能力上建立圆弧视觉令牌和可复用业务组件，包括：

- 颜色、字号、字重、间距、圆角、阴影和层级
- 页面标题、数据卡和标签页
- 筛选栏、日期选择和搜索输入
- 表格工具栏、分页和批量操作
- 状态标签、空状态和骨架屏
- 详情抽屉、确认弹窗和表单反馈

页面可以替换现有组件，但同类交互不得在各页面重复实现互不一致的版本。

### 5.5 业务模块

每个 P0 页面或紧密相关的业务闭环作为独立 feature module，内部管理：

- 页面与局部组件
- 查询和命令状态
- API 契约
- 权限判断
- 测试与 fixtures

不得建立包含全部菜单实现的超大页面文件或超大状态容器。

## 6. 圆弧页面采集

每个页面建立独立页面档案，采集结果必须进入仓库，不能只保存在 AI 对话中。

建议结构：

```text
docs/benchmark/yuanhu/
  manifest.json
  pages/
    index/
      spec.md
      states.json
      screenshots/
    chat-v2-all/
      spec.md
      states.json
      screenshots/
```

页面档案至少包含：

- 菜单分组、路由、标题和面包屑
- `1440x1000` 桌面端基准截图
- 加载、空数据、筛选无结果和异常状态
- 按钮、下拉菜单、分页、弹窗和抽屉
- 表格字段、排序、筛选、批量操作和导出行为
- 表单字段、默认值、校验规则和提交反馈
- 已观测到的请求参数和响应语义
- 权限差异和禁用状态
- 现有项目复用评估
- 页面等级与完成状态

仅采集产品行为、字段和视觉基准，不复制目标系统源码、访问令牌或私有实现。用于 fixtures 的动态数据必须脱敏。

登录失效、套餐限制、目标系统无数据或无法触发的状态标记为“未观测”。未观测行为不得由 AI 猜测后作为一致性实现。

## 7. 数据流与后端边界

P0 页面统一采用以下数据流：

```text
页面交互
→ 前端查询或命令层
→ Go API
→ 权限与租户校验
→ 业务服务
→ 数据库或异步任务
→ 审计记录
→ 前端刷新与状态反馈
```

约束如下：

- P0 页面不得混用模拟数据和真实数据。
- P1 使用独立 fixture/mock 层，升级为 P0 时从生产路径移除。
- 所有业务查询和命令必须遵守租户、企业和权限边界。
- 导出、同步和 AI 分析等耗时操作进入任务中心，不阻塞页面请求。
- 页面需要聚合数据时允许增加专用 Go API，避免前端拼接大量底层接口。
- 列表筛选、分页和关键视图状态通过 URL 恢复，便于演示、分享和排障。
- 真实命令产生的数据在页面刷新和重新登录后仍应正确存在。

## 8. 异常与边界状态

每个 P0 页面必须显式设计并测试适用的状态：

- 首次加载
- 无数据
- 筛选无结果
- 无权限
- 企业未授权或未完成配置
- 网络或服务异常
- 提交冲突和重复操作
- 异步任务进行中、失败与重试
- 登录失效

P1 页面必须至少覆盖正常演示状态和一个无数据状态。P2 页面使用统一建设中状态。

## 9. AI 长任务机制

AI 长任务分为四类并按顺序串联：

1. **采集任务**：浏览圆弧，生成或更新页面档案，不修改业务代码。
2. **设计任务**：对照档案和现有代码，确定复用、修改或替换方式，并定义接口契约。
3. **实现任务**：一次完成一个页面或一个边界明确的业务闭环。
4. **验收任务**：独立运行测试、业务操作和截图比较，不由实现任务自行判定通过。

每个任务必须明确：

- 输入档案和前置状态
- 允许修改的目录或模块
- 不在本任务内的事项
- 必须执行的验收命令
- 需要生成的代码、测试、截图和文档
- 中央清单的状态变更

下一任务只依赖仓库中的档案、清单、代码和测试，不依赖上一段 AI 对话记忆。“完成整个会话模块”之类没有明确终点的任务不得进入执行队列。

## 10. 测试与验收

### 10.1 测试层级

1. **清单测试**：菜单分组、名称、路由、等级和页面注册完整一致。
2. **组件测试**：筛选、表格、表单、弹窗、抽屉和校验行为。
3. **API 与后端测试**：权限、租户隔离、持久化、冲突和异常。
4. **浏览器流程测试**：从菜单进入页面并完成核心业务流程。
5. **视觉回归**：在固定视口比较布局、间距、字体、颜色和关键状态。

第一阶段以 `1440x1000` 桌面端作为强制视觉基线。移动端必须保证可访问、不白屏和不发生破坏性布局溢出，但像素级移动端复刻在桌面端主流程稳定后单独立项。

### 10.2 可演示导航版验收

- 基准清单中的全部菜单和路由可达。
- 全局布局与圆弧基准一致。
- 菜单展开、收起、高亮和刷新恢复正常。
- 浏览器前进、后退和直接访问路由正常。
- 所有 P0、P1、P2 页面均无白屏、404 和控制台错误。
- P1 使用稳定、可重复的演示数据。
- 桌面端视觉回归通过。

### 10.3 单个 P0 页面验收

- 核心业务流程可以真实操作。
- 数据持久化并可在刷新后恢复。
- 权限和租户隔离正确。
- 适用的加载、空、错误和冲突状态齐全。
- 单元测试、API 测试、浏览器流程和视觉回归全部通过。
- 页面档案、接口契约和中央清单已更新。
- 生产路径不存在该页面的 mock 数据。

## 11. 实施顺序

总体顺序为：

```text
全站菜单与页面采集
→ 全局布局和导航复刻
→ 全部登记路由可达
→ P0 数据概览
→ P0 全局消息
→ P0 敏感词
→ P1 高优先级页面
→ 按业务价值把 P1/P2 逐步升级为 P0
```

第一阶段不要求采集全部页面的所有深层交互后才开始全局框架工作。菜单、布局和共性状态采集完成后即可实施全局框架；单个业务页面进入 P0 或 P1 前，必须完成该页面的专项档案。

## 12. 完成定义

项目的最终目标是：

- 已登记菜单和页面在视觉上与圆弧基准一致。
- 相同行为入口产生一致的可观察操作效果。
- 所有目标业务页面最终达到 P0，使用真实权限、真实数据和真实持久化。
- 采集证据、设计决策、实现状态和测试结果可从仓库追溯。

“页面看起来相似但不可操作”“按钮无反馈”“使用 mock 冒充真实结果”或“只有接口没有目标交互”均不视为完成。
