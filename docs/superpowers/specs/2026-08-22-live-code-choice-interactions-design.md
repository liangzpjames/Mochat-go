# 活码成员与群聊选择交互优化设计

> 日期：2026-08-22  
> 状态：已确认，进入实施  
> 适用路由：`/acquisition/v2-channel-code`、`/acquisition/group-code`

## 1. 目标

本轮只优化两个活码创建抽屉中的选择和操作交互：

- 人员选择改为单击切换。第一次单击选中，再次单击同一人员才取消；选择其他人员不得覆盖已有选择。
- 群活码不再向业务用户暴露“群聊配置 JSON”，改为与圆弧 AI 一致的可搜索群聊选择弹窗。
- “取消”和“保存”使用清晰、稳定且一致的底部操作区样式。
- 所有选项来自当前企业权限范围内的真实接口，不使用前端模拟人员、群聊或容量。

本轮保留现有后端必填字段：使用成员、入群引导语、客户标签和群聊关系；不新增海报编辑或自动建群等后端尚未接入的能力。

## 2. 调研结论

圆弧 AI 的“新建群活码”采用“基础设置 → 设置海报”的步骤结构。在基础设置中，群聊不是 JSON 输入，而是点击“选择”打开居中弹窗：

- 左侧是可搜索的真实群聊列表；
- 右侧是已选列表和已选数量；
- 单击一行加入，再次单击同一行取消；
- 继续选择其他群聊会累加，不会覆盖；
- 支持清空选择，最多选择 5 个群；
- 弹窗底部是灰白“取消”和蓝色“确认”圆角按钮；
- 创建抽屉底部使用固定操作栏，主次按钮稳定，不随表单滚动。

当前 MoChat 人员控件使用原生 `<select multiple>`。Windows 浏览器在不按 Ctrl 的情况下单击新选项会替换旧选择，这是“后选覆盖前选”的根因，不是接口或状态同步错误。

## 3. 数据来源矩阵

| 控件 | 前端来源 | API | 关键字段 | 空值与异常语义 |
| --- | --- | --- | --- | --- |
| 使用成员 | 创建抽屉查询 | `GET /workEmployee/index` | `id`、`name`、`status` | 无数据时提示“暂无在职成员”；失败时禁止保存并展示可理解错误 |
| 可加入群聊 | 群活码创建抽屉查询 | `GET /workRoom/roomIndex` | `roomId`、`roomName`、`currentNum`、`roomMax` | 无群聊时展示同步提示；容量不是正整数时不可选择，禁止前端猜测 200 |
| 群聊提交值 | 已选真实群聊派生 | `POST /workRoomAutoPull/store` | `rooms` | 前端内部生成 `[{roomId,maxNum}]` JSON 字符串，用户不可编辑原始 JSON |
| 使用成员提交值 | 已选真实员工派生 | 渠道/群活码既有写接口 | 员工 ID 数组 | 仅提交仍存在于当前权限范围内的正整数 ID |

## 4. 交互设计

### 4.1 人员选择

- 搜索框下展示紧凑成员列表，每项由姓名、选中标记和可点击区域组成。
- 整行都是按钮，普通单击调用 `toggle`：不存在则追加，已存在则删除。
- 已选成员保持在搜索结果中，避免搜索后无法取消。
- 显示“已选择 N 人”，支持逐项取消；不依赖 Ctrl、Shift 或系统原生多选语义。
- 组件同时用于渠道活码和群活码，保证行为一致。

### 4.2 群聊选择

- 表单中展示“可加入的群聊”字段、说明“最多选择 5 个，按选择顺序使用”和“选择群聊”按钮。
- 点击后打开居中双栏弹窗。左侧为搜索结果，右侧为已选顺序。
- 在弹窗内使用草稿状态：点击“确认”才写回表单；点击“取消”、关闭按钮或遮罩均放弃本次草稿修改。
- 单击群聊在草稿中切换，最多 5 个；达到上限后未选项不可继续选择并显示提示。
- 已选区支持单项移除和“清空选择”。
- 每项显示真实群名、当前人数和同步容量；容量无效的群聊显示“容量未同步，暂不可选”。
- 表单仅显示业务信息。保存时自动转换为后端已有 `rooms` 字符串，不展示 JSON、示例或格式校验文案。

### 4.3 底部按钮

- 抽屉底部固定，不随表单内容滚动。
- “取消”和“保存”高度 40px、最小宽度 108px、圆角 999px。
- 取消按钮使用浅灰背景和深灰文字；保存按钮使用蓝色主色与轻微阴影。
- 悬停只改变颜色和阴影，不使用缩放或位移；键盘焦点有清晰轮廓。
- 保存禁用时保持可识别文字和边框，不以过低透明度造成不可读。

## 5. 数据流

```text
员工接口 ──> 员工选项 ──> toggle employeeIds ──> 既有员工提交结构

群聊接口 ──> 群聊选择弹窗 ──> selectedRoomIds（有序）
                               └─> JSON.stringify([{ roomId, maxNum }])
                                   └─> /workRoomAutoPull/store
```

页面只负责把真实选项映射成现有后端契约。本轮不修改数据库、不修改群活码 Provider，也不伪造容量或群聊名称。

## 6. 错误处理

- 员工或群聊查询失败：展示错误提示，相关选择控件和保存保持不可用。
- 搜索无结果：显示“没有匹配的成员/群聊”，不等同于接口未同步。
- 已选对象在查询结果中消失：从有效提交集合中排除，并提示重新选择。
- 群聊达到 5 个：保留已选项，阻止第 6 个并显示上限提示。
- 后端保存失败：保留当前表单与选择状态，展示真实错误，用户可修改后重试。

## 7. 测试与验收

自动化测试必须先失败后通过，覆盖：

1. 连续单击两名员工后两者都选中；再次单击第一名后仅第一名取消。
2. 渠道和群活码共享相同人员切换行为。
3. 群活码创建表单不存在“群聊配置 JSON”。
4. 打开群聊弹窗、选择两项、取消不写回；再次打开并确认后写回。
5. 最多选择 5 个群，容量未同步项不可选择。
6. 保存时 `rooms` 自动映射为有序的 `roomId/maxNum` JSON 字符串。
7. 取消、关闭和保存按钮的可用状态正确。

浏览器验收在 Docker 本地真实路由执行：渠道活码选择两名员工并取消一名；群活码选择两名员工、两条群聊，验证取消/确认、搜索、清空与保存前校验；检查常规桌面与 2560×1440 布局、控制台错误及关键请求。

## 8. 非目标

- 不在本轮实现圆弧 AI 的海报编辑器。
- 不展示当前 Provider 尚未接入的“满 200 人自动建群”开关。
- 不修改客户标签的数据模型或后端必填规则。
- 不提交虚构活码完成浏览器验收；浏览器测试停在保存前，写接口由自动化测试验证。
