# 双分析助手与量化洞察增量设计

日期：2026-08-24  
适用路由：`/ai-setting/ai-knowledge-base`、`/ai-setting/agent`、`/ai-insight/session-analysis`、`/ai-insight/smart-analysis`

## 一、问题与目标

上一版把会话分析和智能分析合并到一个“会话分析助手”，虽然消除了无业务入口的任意智能体和规则创建，但两类分析的目的、提示词和结果模型并不相同。当前还存在四个可验收问题：

1. AI 知识库筛选区的刷新按钮没有复用统一动作按钮尺寸；
2. 助手配置中的会话范围仍是朴素复选框，信息层级和点击面积不足；
3. 会话分析与智能分析共用助手说明和知识库，配置修改会同时影响两类结果；
4. 结果虽已有部分分数，但列表和详情仍以文字为主，员工筛选暴露内部 ID，缺少客户名称筛选。

本轮目标是固定提供两套有明确消费页面的系统助手，分别维护、分别运行、分别展示；增强结果量化结构；修复真实结果持久化阻断；并在保留卷本地环境中使用用户授权的 DeepSeek Provider 生成可识别、可刷新后保留的验收数据。

## 二、精确范围矩阵

| 能力 | 前端 | HTTP/API | 持久化/运行时 | 本轮决策 |
| --- | --- | --- | --- | --- |
| AI 知识库 | `knowledge-base-page.tsx` | `/dashboard/ai-settings/knowledge-bases*`、`documents*` | 知识库、文档、分段、私有文件 | 仅统一刷新按钮尺寸，不改变上传合同 |
| 分析助手 | `agent-page.tsx` | `/dashboard/ai-settings/agents*` | `mochat_go_ai_agents`、设置审计、智能规则版本 | 固定两个系统助手，不开放新增、删除、改名 |
| 会话分析 | `session-analysis-page.tsx`、workspace 组件 | `session-analysis/records|detail|status|export` | 归档消息、洞察结果、运行记录 | 使用会话分析助手；配置客户分析提示词和员工质检提示词 |
| 智能分析 | `smart-analysis-page.tsx`、workspace 组件 | `smart-analysis/records|detail|status` | 系统智能规则及版本、洞察结果、运行记录 | 使用智能分析助手；规则只在该助手内编辑 |
| 查询 | 两个结果页 | records/export 查询参数 | 结果快照字段和数据权限 | 员工名称、客户名称服务端筛选；不再要求记忆 ID |
| 量化结果 | 列表、详情抽屉 | 结构化 JSON DTO | `result_json` | 会话分析与智能分析分别使用受校验的量化 Schema |
| 测试数据 | 无前端假数据 | 既有归档模拟器、Runner | 模拟来源消息、真实 Provider、真实洞察表 | 数据标记为验收模拟来源，保留以供查看 |

情绪识别、员工评分、沟通关键词等其他 AI 洞察路由不在本轮重构范围；Phase 7 真实企微会话存档继续暂停。

## 三、圆弧 AI 调研结论

已在登录态真实点击圆弧的会话分析、智能分析和智能体管理页：

- 会话分析使用客户名称、跟进人姓名/手机号、标签、成交意愿区间和日期查询，不要求输入员工 ID；列表直接展示成交意愿百分比、流失风险和摘要。
- 会话分析详情把“客户分析”和“员工质检”分开。客户侧包含质量等级、成交意愿、流失风险、带权重和分数的维度表、正负因素、需求、情绪和行动建议；员工侧包含总分、未解决问题、未解决异议、话术规范、有效信息比例和风险提示。
- 智能分析页把客户名称、群名称、跟进人和日期作为查询条件，结果列包含关联规则和概述；当前参考租户无数据，不能把未执行工作流宣称为通过。
- 智能体管理以少量固定用途卡片为入口；会话分析策略采用大抽屉、分段规则和即时说明。其业务层级值得借鉴，但复杂策略列表和视觉密度不适合当前 MoChat 两助手场景。

因此本仓库保留“少量固定用途 + 集中配置”的优点，不照搬圆弧的冗长策略表。量化维度采用稳定 Schema 并要求消息证据，避免只有漂亮分数却无法追溯。

## 四、双助手交互模型

### 4.1 固定系统助手

每个租户企业幂等存在：

1. `system_key=session-analysis`，名称固定“会话分析助手”；
2. `system_key=smart-analysis`，名称固定“智能分析助手”。

用户不能新增、删除或改名。列表采用两张紧凑用途卡，不使用筛选、分页和批量操作。每张卡只提供刷新状态、编辑配置和跳转对应洞察页。

### 4.2 会话分析助手

可编辑：

- 运行状态；
- 助手说明；
- 关联知识库；
- 客户分析提示词；
- 员工质检提示词。

两段提示词分别进入模型任务区，但都低于系统安全约束，不能覆盖 JSON Schema、租户边界和证据要求。修改后更新设置指纹，使下一轮重新分析；写入设置审计。

### 4.3 智能分析助手

可编辑：

- 运行状态；
- 助手说明；
- 关联知识库；
- 智能分析目标；
- 会话范围、回看天数、最少消息数。

智能分析目标继续使用不可变规则版本保存历史快照，但界面称“智能分析规则”，不再出现“默认智能体”或“默认智能分析规则”。会话范围改为整卡可点的双选选项：图标/标题/说明/选中态共同构成点击目标；键盘、焦点态和窄屏换行可用。

### 4.4 关闭与失败

- 两助手独立启停；停用一个不影响另一个。
- Provider 不可用、助手停用、模型响应不合法、数据库写入失败均记录真实失败，不生成伪成功结果。
- 编辑器支持遮罩、Escape 和关闭；有未保存更改时先二次确认。

## 五、数据与运行时设计

### 5.1 助手配置

复用已有规则与不可变规则版本链，不另造提示词版本基础设施：新增会话系统规则，在规则表和版本表保存受服务端校验的 `customer_analysis_prompt` 与 `employee_qa_prompt`；会话结果开始记录对应 `rule_id/rule_version_id`，使历史提示词可追溯。新增智能分析助手时继承原助手知识关联一次，之后独立维护。

智能规则的持久化 `system_key` 为兼容历史数据保持不变，但公开名称迁移为“智能分析规则”，代码和界面不再表达“默认智能体”或“默认规则”。

### 5.2 独立运行上下文

Runner 按分析类型加载对应助手上下文、知识库、状态和设置指纹：

```text
会话归档候选 ──> 会话分析助手 ──> 客户分析 + 员工质检 Schema
             └─> 智能分析助手 ──> 智能分析规则 + 通用量化 Schema
```

任一助手加载失败只关闭对应分析类型。洞察状态接口返回当前页面对应助手的名称、启停、知识库数和就绪文档数。

### 5.3 写库缺陷

只读审计和保留库运行记录表明：结果 INSERT 的 27 列与 VALUES 数量不一致，最近会话运行有候选但全部以 MySQL 1136 失败。必须先增加真实 MariaDB 插入/更新集成测试复现，再修正占位符；未修复前不得宣称 Provider 或测试数据链路通过。

## 六、量化结果 Schema

### 6.1 会话分析

列表突出三个数：购买意向、流失风险、员工质检总分。详情分“客户分析 / 员工质检 / 证据消息”标签：

- 客户质量：0–100 分、等级、理由；
- 购买意向：0–100 分、等级、维度（需求强度、决策进度、价格敏感度、信任指数、时效压力）；
- 流失风险：0–100 分、等级、维度（竞品替代、决策复杂度、资金、技术/交付）；
- 每个维度包含名称、权重、分数、理由和 `evidenceMessageIds`；
- 员工质检：0–100 总分、维度分、未解决客户问题、未解决异议、优点、问题和改进建议；
- 证据 ID 必须属于同一模型请求的归档消息。

无足够证据时分数为 `null` 或标记证据不足，不以 0 分冒充判断。

### 6.2 智能分析

列表突出命中度和优先级，详情展示：

- 命中度 0–100；
- 结论置信度 0–100；
- 证据覆盖度 0–100；
- 行动优先级分 0–100 与低/中/高等级；
- 由目标驱动的量化维度、结论、证据和建议。

这些数值是模型基于真实会话按固定含义输出，经服务端范围和证据校验后持久化；前端不自行计算或补默认分数。

## 七、查询、URL 与权限

- 两页的员工条件改成可搜索姓名的组合框；选项由页面同权限的 `filter-options` 接口返回，只包含当前分析类型有结果且当前操作者有权查看的员工。请求和 URL 内部仍保存稳定 `employeeId`，界面只展示姓名。
- 两页增加 `customerName` 明文输入，服务端在当前 tenant/corp、当前员工数据范围内对结果快照做转义后的模糊匹配。
- 客户名称只匹配客户单聊对象；群聊继续可用关键词/会话类型查询，避免把群名误称客户名。
- records、detail、status、export 均沿用现有 RBAC 资源；详情和证据再次校验员工范围。
- 助手读写沿用 `/ai-setting/agent#read|manage`，所有更新绑定服务端 Principal 的 tenant/corp/actor，忽略客户端越权身份字段。

## 八、视觉与响应式原则

- 使用当前已验收 Dashboard 的 36px 动作按钮、8px 圆角、主次按钮色和间距；知识库刷新与查询/重置同高同内边距。
- 两助手卡在常规桌面并排，窄屏纵向；配置弹窗内容分节，短高度下仅正文滚动、底部动作可见。
- 会话范围选择卡桌面两列、窄屏一列；复选框保留原生语义，整卡有 hover/focus/selected 状态。
- 结果列表在宽屏优先展示量化指标，窄屏允许横向滚动；详情抽屉桌面不超过 760px，移动端全宽。
- 所有分数同时显示文字标签，不只依赖颜色。

## 九、测试数据与 Provider 边界

- 用户提供的 API 密钥只写入本机受保护 Docker 运行时配置，不进入仓库、Git、截图、日志或报告。
- 官方 DeepSeek 文档当前公开模型名为 `deepseek-v4-flash`，用户口语“ds-flash”按该官方模型落地；使用 OpenAI 兼容基址 `https://api.deepseek.com`。
- 测试会话由既有 archive simulator 写入持久化归档链路，并明确携带模拟来源命名空间；不使用前端静态数组或直接伪造洞察结果。
- 触发真实 Runner 后，以 Provider 返回、Schema 校验、洞察写库、API 查询和浏览器刷新仍存在作为通过条件。外部调用失败则保留清晰失败状态并如实报告。

## 十、验收标准

1. AI 知识库刷新与同组按钮尺寸一致；
2. 分析助手页仅有两个固定助手，分别编辑、分别启停、分别关联页面，不出现“默认智能体”；
3. 两段会话分析提示词可保存、刷新恢复、进入对应模型任务；智能规则只在智能分析助手编辑；
4. 两结果页可按员工名称和客户名称查询，URL 刷新可恢复；
5. 会话与智能结果列表、详情均展示服务端持久化量化指标和证据；
6. 真实 MariaDB 写入缺陷有红绿测试，真实 Provider 运行至少生成一组成功结果；
7. 权限、租户、员工范围、提示词长度、分数范围和证据 ID 均有自动化覆盖；
8. 桌面、窄屏、小高度下查询、编辑、关闭/Escape、空态、失败态和刷新后持久化通过浏览器验收。
