# 消息拦截、关键词库与沉默客户菜单优化设计

> 文档日期：2026-08-21
> 审阅状态：待用户审阅，尚未开始实施
> 目标路由：`/ai-insight/v2/message-intercept`、`/ai-insight/v2/keyword-library`、`/ai-insight/v2/silent-customer`

## 1. 目标与本轮停止点

本轮只完成三个菜单的设计与实施计划，不修改业务代码、不构建、不部署。用户审阅通过后再进入测试先行的开发实施。

设计目标：

1. 保留现有菜单导航、菜单名称和路由；移除风险预警子菜单重复的顶部 banner；
2. 复用已经落地的风险预警工作台骨架，移除三个页面的纯介绍大卡和重复刷新；
3. 借鉴圆弧 AI 的信息层级、查询密度、左右栏和分页节奏，不复制其企业数据、字段或不可验证能力；
4. 消息拦截形成“规则配置—归档消息检测—命中记录—人工复核”的真实闭环；
5. 关键词库形成“词库—草稿词条—发布版本—规则引用”的真实闭环；
6. 沉默客户形成“规则配置—归档会话评估—沉默明细—分派/跟进—审计”的真实闭环；
7. 所有查询使用真实接口、显式提交、固定每页 20 条并写入 URL；
8. 页面不出现“能力未接入”“数据提供方未接入”等占位说明。只能后续专项完成的能力记录到 `docs/PROJECT_PROGRESS.zh-CN.md`；
9. 以 `2560×1440` 为主要验收尺寸，同时回归当前常规桌面宽度；
10. 开发完成后必须自行点击验证布局、按钮样式、筛选、分页、弹层、确认、刷新和数据持久化。

## 3. 方案比较与结论

### 方案 A：保留现有组件，只调整颜色和间距

- 优点：改动最少；
- 缺点：输入即请求、无分页、内部 ID、技术字段详情、自动扫描断点和状态持久化问题都不会解决。

### 方案 B：合并成单一“风险内容中心”

- 优点：规则、词库和记录可放在一个页面；
- 缺点：改变现有三个菜单路径；一个页面同时承载版本发布、规则、复核和客户跟进，职责过重，权限边界也更难理解。

### 方案 C：共享工作台骨架，保留三个独立领域页（采用）

三个页面复用标题、标签、查询栏、状态条、表格、分页、抽屉和确认样式；关键词库、拦截规则、沉默客户分别使用类型化 API 和独立数据模型。消息拦截引用关键词库的已发布版本，沉默客户独立消费归档会话活跃度。

该方案既保持现有菜单语义，又能完整修复数据链和交互问题。

## 4. 共享页面设计

### 4.1 页面骨架

1. 使用现有 `RiskWarningShell`，页面内容区取消固定窄宽；
2. 子菜单不再渲染重复的顶部 banner，业务标题和主操作放在各自的查询栏或工作区工具栏内；
3. 查询、重置、刷新集中在 `RiskWarningQueryBar`，页头不再放第二个刷新；
4. 查询输入使用 `draftFilters`，只有点击“查询”或回车才写入 `appliedFilters`；
5. 标签切换、已提交筛选、页码和选中详情 ID 写入 URL；刷新后可以恢复；
6. 列表固定每页 20 条，统一使用 `DashboardPagination`；
7. 整行可打开详情，复选框、开关、链接和行内按钮阻止冒泡；
8. 抽屉支持关闭按钮、遮罩和 `Escape`，关闭后焦点返回触发行；
9. 后台刷新保留旧列表，不闪回全屏加载；
10. hover 只改变颜色、背景和边框，不使用位移、缩放或模糊效果。

### 4.2 数据状态

页面仅使用以下用户可理解状态：

- 首次加载：骨架或轻量加载态；
- 空数据：说明当前筛选下没有记录，并提供重置筛选；
- 请求失败：保留筛选条件和已有列表，显示重试；
- 无权限：显示当前企业/员工范围不可访问；
- 后台扫描异常：使用一条紧凑状态条说明“最近一次检测失败/尚未运行”，不使用“能力未接入”文案；
- 写操作失败：弹层保持打开，字段值不丢失，错误定位到当前动作。

产品层面确实无法由本轮页面和服务端完成的内容只写总进度文档，不在页面重复展示。

## 5. 消息拦截页面

### 5.1 信息架构

页面标签按业务顺序排列：

1. `拦截规则`（默认）：规则是页面的配置入口，与圆弧 AI 主页面一致；
2. `命中记录`：展示归档消息检测结果并完成复核。

页面不承诺企业微信发送前真正阻断。MoChat 本轮实现的是“归档消息到达后自动检测、形成拦截记录并进入复核”，但菜单名称保持不变。

### 5.2 拦截规则

查询条件：规则名称、状态、处置方式。主操作为“新增规则”。

表格列：规则名称、词库与版本、会话范围、命中处置、命中次数、启用状态、更新时间、操作。

新增/编辑使用右侧抽屉：

- 规则名称；
- 已发布词库版本；
- 会话范围：客户单聊、客户群聊；
- 命中处置：标记拦截、进入复核、仅记录；
- 启用状态。

规则保存时服务端再次校验词库属于当前企业、版本已发布、会话范围合法。旧样例值 `customer/room` 在数据库迁移中规范为 `single/group`，前端不做永久兼容分支。

启停和删除必须确认。规则删除统一采用 `deleted_at` 软删除；历史命中记录继续显示保存时的规则名称和词库版本，列表默认排除已删除规则。

### 5.3 命中记录

查询条件：消息/命中词、规则、会话类型、处置方式、复核状态、开始/结束日期。现有历史值 `reviewed` 统一显示为“已复核”并保持只读兼容；新复核动作只写 `confirmed` 或 `ignored`。

表格列：发送者、会话类型、消息摘要、命中词、规则、检测结果、复核状态、发生时间。

详情抽屉显示业务字段，不枚举原始对象：

- 发送者、会话对象和发生时间；
- 消息正文；
- 命中关键词；
- 规则、词库名称和固定版本；
- 检测解释；
- 复核状态和审计历史；
- 可验证时提供“查看会话”跳转。

待复核记录支持勾选后批量“确认违规”或“忽略”。批量工具条显示已选数量，动作成功后展示成功/失败数量并重新请求服务端；不靠前端隐藏维持结果。

### 5.4 自动数据流

```text
企业微信会话存档同步
        ↓
mc_work_message_1 ... mc_work_message_10
        ↓ 独立游标、幂等扫描
启用的拦截规则 + 固定词库版本
        ↓
mochat_go_message_intercept_records
        ↓
命中记录列表 / 详情 / 人工复核审计
```

扫描只处理当前游标后的归档消息，按 `corp_id + rule_id + message identity` 幂等。失败时不推进越过失败消息的游标，避免漏检。

## 6. 关键词库页面

### 6.1 双栏工作区

```text
┌──────────────────┬───────────────────────────────────────────────────┐
│ 词库列表 260px   │ 选中词库摘要 / 草稿状态 / 发布状态               │
│ 搜索、新建       │ 关键词查询、状态筛选、添加词条、发布新版本       │
│ 名称、状态、数量 │ 词条表格、固定分页                               │
└──────────────────┴───────────────────────────────────────────────────┘
```

左侧词库显示名称、状态、启用词条数、草稿版本和已发布版本。选择词库只更新右侧，不改变列宽。没有选中时显示“请选择一个词库”，不出现能力说明。

右侧顶部清楚区分：

- `草稿 vN`：当前可编辑词条；
- `已发布 vN`：拦截规则引用的不可变快照；
- “有未发布修改”只由真实版本/更新时间关系计算。

### 6.2 词条管理

查询条件：关键词、状态。表格列：关键词、状态、更新时间、操作。

新增支持用换行、逗号、顿号和分号拆分多个词条；提交前去空、去重并显示有效数量。前端通过新增批量接口一次提交，服务端在事务中维持同一词库内唯一约束，并返回逐项新增/重复结果。

启停、编辑和删除都只修改草稿。只有点击“发布新版本”并确认后，才生成新的不可变版本供新规则引用；已有规则继续引用原版本。

删除词库前服务端检查是否被任何未删除规则或历史版本引用。被引用时不允许删除，页面展示明确的规则名称；从未被引用的词库二次确认后物理删除。

### 6.3 不采用圆弧白名单标签

当前 MoChat 没有可追溯的白名单存储、匹配优先级或规则引用协议。本轮不创建白名单标签、空页或禁用按钮，也不在页面显示“未接入”。若以后立项，应作为独立规则语义设计，不与关键词草稿混用。

## 7. 沉默客户页面

### 7.1 信息架构

页面保留两个有真实数据支撑的标签：

1. `沉默明细`（默认）；
2. `规则配置`。

不添加圆弧 AI 的管理看板、任务中心、我的任务、群目标和数据分析入口，因为当前数据模型不足以支撑这些页面。

### 7.2 沉默明细

查询条件：客户关键词、原归属员工、当前负责人、沉默天数区间、跟进状态、快照日期。状态完整覆盖待跟进、已分派、已跟进、已唤醒、已忽略和已关闭。

员工条件使用与员工会话统一的真实部门/员工选择组件，显示员工姓名和部门，不要求填写内部 ID。

表格列：客户、原归属员工、沉默天数、最后互动时间、当前负责人、跟进状态、更新时间、操作。

详情抽屉显示：

- 客户及原归属员工；
- 命中规则和阈值；
- 最后互动时间与当前沉默天数；
- 当前负责人；
- 跟进状态、备注和完整审计时间线；
- 有真实会话标识时提供“查看客户会话”。

勾选记录后出现批量工具条。分派动作打开小型确认弹层，使用员工选择器和备注；“已跟进”“已唤醒”“关闭”按状态机限制可用动作。每次动作必须写审计记录并从服务端重新读取，刷新页面后结果保持一致。

### 7.3 规则配置

查询条件：规则名称、状态。表格列：规则名称、沉默阈值、当前命中数、状态、更新时间、操作。

规则抽屉字段：规则名称、连续无互动天数（1–365）、启用状态。规则启停和删除需要确认；规则删除统一采用 `deleted_at` 软删除，已有沉默记录继续保留规则名称快照。

### 7.4 自动评估数据流

```text
客户关系 + 真实归档会话
        ↓
按企业、客户、归属员工聚合最后互动时间
        ↓
启用的沉默规则
        ↓ 每日/周期性幂等评估
mochat_go_silent_customer_records
        ↓
沉默明细 / 分派 / 跟进 / 审计
```

评估以归档消息中员工或客户最后一次有效互动为准，不使用浏览页面触发写入。重新评估时：

- 首次达到阈值：新增 `pending` 记录；
- 仍然沉默：更新快照时间和天数，不覆盖人工负责人、状态和备注；
- 已恢复互动：将未关闭记录转为 `awakened` 并写系统审计；
- 同一客户命中多条规则：按最严格的已启用阈值生成或更新对应规则记录，保持现有唯一键语义。

空值不必写入 URL；页大小固定 20，不对用户开放不一致的页大小。

## 10. 权限与安全

1. 列表和详情继续按当前企业、租户和员工范围过滤；
2. 规则/词库配置与记录复核、沉默分派分成不同 action 资源，不能只靠“看得到页面”推导写权限；
3. 前端根据资源权限隐藏或禁用主操作，后端仍作最终校验；
4. 批量动作只处理请求者有权访问的记录，并返回逐项结果；
5. 消息内容、备注和审计详情不写入 URL、日志或错误堆栈；
6. 删除动作保留历史快照或阻止删除，不能破坏已有审计链；
7. 自动扫描使用独立开关、游标、幂等键和状态记录，默认不因页面访问而启动。

## 11. 开发数据

开发阶段允许补充可重复的本地样例，但必须满足：

- 只在显式本地开发脚本中生成；
- 使用稳定前缀和幂等 upsert；
- 覆盖启用/停用、待复核/已复核、待跟进/已分派/已唤醒等测试状态；
- 不在前端写静态数组；
- 不覆盖真实企业数据；
- 生产环境不自动执行。

## 13. 明确不在本轮页面中展示的后续专项

企业微信官方会话存档只能在消息产生后拉取，当前 MoChat 没有员工发送端插件或客户端 SDK，因此无法由 Dashboard 和现有后端实现真正“发送前阻断并即时提示员工”。本轮会把归档后自动检测和复核闭环做完整，同时把发送前阻断作为独立客户端专项记录到总进度文档；页面不出现“能力未接入”提示，也不伪装成已在发送前阻止。

## 14. 审阅结论待确认

本设计默认采用以下产品决策：

1. 消息拦截默认打开“拦截规则”，命中记录作为第二标签；
2. “拦截”在本轮表示归档后检测结果与合规处置，不宣称发送前阻断；
3. 关键词库不增加没有真实模型的“白名单”标签；
4. 沉默客户只覆盖客户，不伪造群沉默和分析看板；
5. 三个页面共用风险预警工作台，但保持独立路由、权限和数据模型。
