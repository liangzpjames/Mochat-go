# 文档阶段化与总进度重建设计

## 目标

将 `docs/` 从按用途和会话零散堆放的结构，重组为按开发阶段归档的单一事实源。开发者应能从一个总进度入口判断项目当前阶段、各阶段完成状态、现有阻塞和下一项实施任务，并能回溯每个阶段开始前与结束时的项目状态。

## 设计原则

1. `docs/PROJECT_PROGRESS.zh-CN.md` 是项目开发总进度的唯一入口。
2. 每个阶段使用独立目录，并以该目录的 `README.md` 作为阶段状态入口。
3. 计划、设计、验收、审计和证据分开保存，避免会话交接文档承担长期事实源职责。
4. 保留最终有效证据、审计矩阵和仍有合规价值的历史记录。
5. 删除重复副本、零字节临时日志、被最终版覆盖的候选快照及无有效信息的会话文件。
6. 任何被脚本或代码引用的文档路径必须先更新引用，或者保留明确的兼容入口。
7. 文档整理不改变产品代码、数据库、部署配置或现有阶段完成结论。

## 阶段定义

### Phase Pre-0：独立版与 SaaS 能力收口

保存 Phase 0 之前形成的独立版差距、发布候选、SaaS Admin MVP、生产证据和商业化交接结论。超长追加式报告不继续作为活动进度入口；保留其最终结论和仍有效的发布证据，历史细节按价值进入归档。

### Phase 0：Go 工程底座

保存架构设计、实施计划、检查表、验收结果、需求/风险/缺陷/资源与生产证据登记表。阶段 README 明确开始条件、完成项、遗留限制和交付提交。

### Phase 1：前端统一底座

保存前端统一底座计划、验收结果、前端审计矩阵、证据、迁移 Runbook，以及 SaaS Admin Docker 发布纠偏记录。阶段 README 必须区分“基础设施完成”和“产品界面尚未全量迁移”。

### Phase 2：前端逐页迁移

作为当前待实施阶段，保存全量迁移批次计划、每批验收和路由切换记录。初始状态明确记录当前只有 `/corp/index` 为 React 业务页面、60 条 Dashboard 路由仍为 legacy、Sidebar 与 Operation 尚未迁移。

## 总进度文档

`PROJECT_PROGRESS.zh-CN.md` 包含：

- 项目当前阶段和总体结论；
- 阶段状态表：状态、完成比例口径、开始条件、完成定义和入口；
- 当前可运行、可测试与不可测试范围；
- 已知阻塞和风险；
- 当前精确下一任务；
- 最近一次验证与提交；
- 文档维护规则。

完成比例按阶段任务和验收项计算，不使用主观估值。尚未形成逐任务计划的阶段标记为“未基线化”，不虚构百分比。

## 文件处置规则

### 保留并迁移

- 已批准的架构设计和实施计划；
- 最终验收、检查表、风险/需求/缺陷登记表；
- 前端审计 CSV 和许可证记录；
- 仍有效的产品范围、协议和本地开发说明；
- 最终生产证据和源码指纹。

### 合并后归档或删除

- 会话交接中的有效状态合并至阶段 README；
- 多次追加的阶段报告提炼为阶段总结；
- 同一候选的重复副本只保留最终有效版本；
- 已被最终验收覆盖的临时候选说明进入归档，且不出现在活动索引。

### 删除

- 文件名含 ` 2` 的重复副本，前提是内容已由正式文件覆盖；
- 零字节日志和空的运行快照；
- 无独立信息、无引用且已被新文档完整取代的临时文档；
- 过时的会话级占位文件。

删除前逐个验证目标是 Git 跟踪文件、内容确属重复或空白，且不再有有效引用。

## 引用兼容

整理前扫描仓库内所有 `docs/` 路径引用。对于脚本读取或写入的固定路径，优先更新脚本到新路径，并同步更新其测试。只有外部兼容需求无法验证时，才保留旧路径的简短索引文件；不保留内容重复的完整副本。

## 验证

实施完成后执行：

1. 枚举 `docs/`，确认所有活动文档均进入阶段或参考目录；
2. 扫描 Markdown 相对链接，确认目标文件存在；
3. 扫描代码和脚本中的旧文档路径，确认没有失效引用；
4. 检查重复文件名、` 2` 副本和零字节文件；
5. 运行受文档路径影响的脚本测试或快速门禁；
6. 检查 `git diff --check` 和最终删除清单；
7. 提交到当前 `main`，再推送 `origin/main`。

## 完成标准

- 总进度文档能明确回答项目当前进度、各阶段状态和下一任务；
- 每个已存在或即将开始的阶段都有独立入口；
- 开发者可回溯每阶段开始前和结束时的状态；
- 活动文档中不存在重复候选、空日志或失效链接；
- 代码与脚本引用未因移动文档而失效；
- 整理结果已提交并成功推送至 `origin/main`。
