# 客户会话圆弧式工作台改造设计方案

## 1. 范围与目标

本轮只设计菜单“会话 → 客户会话”，目标路由为 `/chat/v2-customer`。菜单导航、应用顶部 banner、企业切换和全局搜索保持不变；员工会话、群聊会话、会话轨迹、会话导出及其他页面不在本轮联动改造。

目标不是给现有会话卡片换色，而是参照圆弧 AI 客户会话的连续工作台结构，把页面重组为“客户目录 → 关联会话 → 消息阅读”三栏。所有客户、员工、群聊、消息、统计、关注状态和能力提示必须来自 MoChat 的真实数据链路，并始终使用同一 tenant、corp、员工数据权限和会话归档来源。

本设计文档完成后暂停，等待用户审阅；本轮不实施代码。

## 2. 当前基线与问题

### 2.1 MoChat 当前页面

当前 `/chat/v2-customer` 仍通过 `ConversationGlobalPage(fixedConversationType="customer")` 渲染，具备关键词、员工 ID、日期、消息类型、分页、会话详情抽屉和重点关注等基础能力，但不符合客户会话的使用路径：

1. 页面以概览指标、通用筛选和会话卡片为主，用户不能先选客户，再查看该客户与不同员工或客户群的历史沟通。
2. 固定客户类型后仍展示“群聊会话、群聊消息、群聊覆盖员工”等全局指标，信息与当前页面任务不一致。
3. 客户、员工和消息上下文分散在卡片与抽屉中；切换客户需要重新组合筛选条件，无法连续阅读。
4. 员工筛选要求输入原始员工 ID，不适合日常操作，也会把内部标识暴露为主要交互。
5. 当前详情只读取最近 200 条消息，不能按游标加载更早消息；统计和详情筛选能力不足。
6. 图片、链接、文件、视频、语音等归档内容没有稳定的类型化展示。
7. 本地 2560×1440 实测出现“会话总量 11、当前页 15 条”的口径不一致，同一员工与客户会话也会以不同最后消息重复出现。列表和总数必须改为基于同一去重会话集合计算。
8. 当前页面复用了全局消息的视觉结构，宽屏主要用于横排概览卡和卡片网格，没有形成高效的客户检索、会话选择和消息阅读工作区。

### 2.2 圆弧 AI 参考页

参考页 `/chat/v2-customer` 在 2560×1440 下采用完整高度的连续三栏：

- 左栏：客户列表/重点关注、客户搜索、客户分页，以及底部客户状态入口。
- 中栏：选中客户信息、单聊/群聊切换，以及该客户关联的会话列表。
- 右栏：选中会话标题、刷新等动作、消息类型、内容和日期检索、会话统计及消息流。
- 三栏之间只用细边框分隔，右栏获得绝大多数宽屏剩余空间，各栏内部独立滚动。

本设计只借鉴参考页的信息架构、栅格、密度和交互顺序。圆弧页面中的客户、企业、聊天内容、统计数字、智能摘要、会话下载和其他商业能力不复制到 MoChat。

## 3. 方案比较与决策

### 方案 A：保留通用卡片页，仅调整 CSS

保留 `ConversationGlobalPage`、概览卡片、筛选区和详情抽屉，只改变列数、颜色与间距。优点是改动最小；缺点是仍然缺少客户目录、跨员工关联会话和客户所在群聊，无法解决重复会话与统计口径问题。拒绝。

### 方案 B：前端拼接现有联系人和会话接口

左栏调用 `/workContact/index`，中栏调用 `/workMessage/toUsers`，群聊再调用客户群接口，前端自行合并。优点是后端新增较少；缺点是联系人接口按客户—员工关系行分页，不是按客户去重分页，并且联系人菜单权限、会话权限、归档范围和群成员范围可能不一致。前端也无法可靠计算重点关注、流失状态、会话总数和群聊关联。拒绝。

### 方案 C：客户会话专用工作台契约（采用）

在现有会话权限域内新增客户目录、客户关联会话和客户会话详情契约。后端复用联系人、客户—员工关系、客户群成员、归档消息、关注记录和访问范围，统一完成去重、聚合与权限裁剪；前端只负责 URL 状态、三栏联动和展示。

该方案工作量高于纯前端改造，但可以保证客户目录、单聊、群聊和详情来自同一数据口径，并为宽屏工作台提供稳定接口。现有 `ConversationMessageContent`、关注接口和员工会话的消息游标查询可复用，避免重复实现底层消息解析。

## 4. 页面结构

```text
┌──────────────────────────────── 客户会话工作台 ────────────────────────────────┐
│ 客户目录 288px        │ 关联会话 360px           │ 消息阅读 minmax(0, 1fr)      │
│ 客户列表 | 重点关注   │ 客户名称/资料状态         │ 会话对象 + 员工 + 刷新/关注  │
│ [客户搜索] [刷新]     │ 单聊 | 群聊               │ 消息类型 + 内容 + 日期        │
│ 客户列表              │ 会话卡片                  │ 沟通天数/消息/双方发送统计    │
│ 头像/名称/最近沟通    │ 员工或群聊/摘要/时间       │ 消息时间轴                    │
│ 固定分页              │ 固定分页                  │ 加载更早消息                  │
│ 有效关系 | 已流失     │ 能力与关系状态提示         │ 缺口提示                      │
└───────────────────────────────────────────────────────────────────────────────┘
```

工作台使用一个外框，三栏之间只保留 1px 分隔线，不给每栏增加独立阴影和大间距。页面不增加顶部标题卡或介绍容器，内容区从主布局顶部直接开始。

### 4.1 左栏：客户目录

- 顶部主页签为“客户列表”和“重点关注”，数字分别表示当前权限范围内存在可访问归档会话的去重客户数，以及至少有一条当前用户已关注直接会话的客户数。
- 搜索按客户名称、备注名和企业微信外部联系人标识匹配；页面只展示名称，不把外部联系人标识作为主文案。
- 客户列表按最近会话时间倒序，每页固定 50 个去重客户，使用普通分页，不把客户—员工关系行误当成独立客户。
- 每项展示真实头像或文字头像、客户名称、最近沟通时间、关联单聊数、关联群聊数；当前资料缺失时显示“客户资料未同步”，但保留可访问的归档会话入口。
- 底部快捷筛选为“有效关系”和“已流失”。有效关系指当前权限范围内至少有一条 `mc_work_contact_employee.status=1` 且未删除的关系；已流失指没有有效关系，但至少存在一条 `status IN (2,3)` 的历史关系。
- 同一客户同时存在有效和历史关系时归入“有效关系”，避免两个底部状态重复计数；历史关系仍可在中栏单聊卡片上标识。
- “重点关注”只根据该客户的直接会话关注记录计算。客户所在群聊的关注属于群会话，不反向计入客户目录，避免一个群的关注影响多个客户。
- 刷新只重取客户目录，不改变 URL、当前模式或输入内容。

### 4.2 中栏：关联会话

- 选中客户后显示客户名称、头像和资料状态，并提供“单聊”“群聊”两个页签。
- 单聊按员工—客户稳定会话聚合，每张卡对应 `employeeId:1:customerId`，展示员工、最近消息时间、摘要、消息总数，以及真实存在的风险、超时、关注和关系状态。
- 群聊通过 `mc_work_contact_room` 将选中客户与客户群关联，再与归档群消息求交集。每张卡对应 `employeeId:2:roomId`，展示群名称、归档员工、最近消息和成员状态。
- 同一客户群被多个可访问员工归档时，不擅自合并成一条。每个员工—群会话分别展示并明确员工名称，避免选择一个“代表员工”后丢失其他归档范围。
- 客户已退出某群但仍有历史归档消息时，卡片显示“已退群”；没有任何归档消息的群不进入会话列表。
- 整张卡片可点击。切换客户、客户目录模式或单聊/群聊时，清空已选会话并回到第 1 页。
- 每页固定 20 条，会话列表和总数必须从同一去重、排序后的查询集合产生，禁止再次出现 `total < list.length`。
- 群聊消息当前不能从归档字段稳定识别具体外部群成员。群聊页签和详情必须显示能力提示，不能把所有入站消息标成当前客户发送。

### 4.3 右栏：消息阅读

- 标题显示会话对象、会话类型和归档员工。单聊显示客户名称，群聊显示群名称和“客户所在群聊”关系。
- 动作只保留“刷新”和“重点关注/取消关注”。刷新只刷新当前详情；关注成功后同步刷新当前卡片和客户目录关注数。
- 不展示参考页的“会话下载”“智能摘要”和“会话轨迹”动作。当前系统没有完整单会话下载和会话级 AI 摘要合同，会话轨迹页也没有稳定的单会话深链，不能伪装为可用能力。
- 筛选区包含消息类型多选、内容关键词和单日日期。筛选只影响消息时间轴，不改变中栏会话列表和完整会话统计。
- 初始读取最新 50 条消息，按时间正序显示；点击“加载更早消息”使用后端不透明游标向前读取，每次 50 条。
- 单聊统计展示“沟通天数、消息总数、客户发送、员工发送”。群聊统计展示“沟通天数、消息总数、非员工消息、员工发送”，明确“非员工消息”不能等同于当前客户消息。
- 统计始终按完整会话计算，不用当前已加载的消息页在前端推算，也不随消息筛选变化。
- 文字、图片、链接、文件、视频、语音等内容复用 `ConversationMessageContent`。只有归档内容包含可用字段时才展示预览或链接；字段不足时显示“该类型内容暂不支持预览”，不构造地址、文件名或缩略图。

## 5. 响应式与尺寸

- 视口宽度 ≥ 1600px：工作台占满内容区，列宽为 `288px 360px minmax(560px, 1fr)`；2560×1440 下右栏吸收全部剩余宽度。
- 视口宽度 1200–1599px：客户目录改为可开合左侧抽屉，中栏固定 360px，右栏至少 520px，不能把消息栏压成窄条。
- 视口宽度 769–1199px：默认显示关联会话与消息详情；客户目录从左侧抽屉打开。选择会话后允许收起中栏以扩大消息区。
- 视口宽度 ≤ 768px：客户、会话和详情采用分步单栏；返回操作恢复上一级及 URL 状态。
- 工作台高度使用 `calc(100dvh - 应用头部高度 - 内容区垂直间距)`，三栏各自滚动。长消息只滚动右侧消息区，不把页面整体高度无限撑开。
- 主验收尺寸为 2560×1440，同时回归 1440×900、1066×1272 和 390×844。

## 6. URL 与状态规则

Canonical URL：

```text
/chat/v2-customer?
customerMode=all&customerKeyword=&customerPage=1&customerId=2001&
conversationMode=direct&page=1&pageSize=20&
conversationId=9:1:2001&messageKeyword=&messageTypes=image,file&messageDate=2026-08-16
```

- `customerMode`：`all | focused | active | lost`，默认 `all`。
- `customerPage`：客户目录页码；客户页大小固定 50，不接受 URL 自定义。
- `customerId`：正整数客户 ID。客户搜索或目录模式改变时清空。
- `conversationMode`：`direct | group`，默认 `direct`。
- `page`：当前关联会话页码；`pageSize` 只接受 20，非法值替换为 20。
- `conversationId`：稳定格式 `employeeId:toUserType:toUserId`。直接会话的 `toUserType=1` 且 `toUserId=customerId`；群会话的 `toUserType=2` 且后端必须验证群与 `customerId` 的成员关系。
- `messageTypes`：可重复参数；`messageKeyword` 和 `messageDate` 只作用于右栏。
- 消息游标不写入 URL。刷新页面后从最新 50 条重新读取；客户页、客户、会话页、会话和消息筛选可以恢复。
- URL 中的客户或会话不在当前数据权限时返回 404 状态，不自动切换到其他对象，避免泄露对象是否存在。

## 7. 后端契约

三个新增读取接口均沿用客户会话页面的会话权限域，不要求用户额外拥有 SCRM 联系人菜单权限。处理器必须从 principal 获取 tenant、corp、user 和允许员工集合，忽略客户端提交的 tenant/corp 范围。

### 7.1 客户目录

新增：

```http
GET /dashboard/workMessage/customerDirectory
  ?mode=all&keyword=&page=1&pageSize=50
```

响应：

```json
{
  "customers": [{
    "id": 2001,
    "name": "陈晓明",
    "avatar": "",
    "profileStatus": "available",
    "activeRelationCount": 2,
    "lostRelationCount": 0,
    "directConversationCount": 2,
    "groupConversationCount": 1,
    "focusedConversationCount": 1,
    "lastConversationAt": "2026-08-16 13:50:08"
  }],
  "counts": { "all": 8, "focused": 2, "active": 7, "lost": 1 },
  "page": 1,
  "pageSize": 50,
  "total": 8,
  "limitations": [],
  "capabilities": [{
    "key": "groupMemberIdentity",
    "available": false,
    "reason": "当前归档数据无法稳定识别群聊入站消息的具体外部成员"

目录基础集合为当前员工权限范围内具有直接归档会话，或具有“客户群成员关系 + 可访问群归档会话”的去重客户。客户主数据不存在或已软删除时仍可使用归档中的名称展示，`profileStatus` 返回 `missing` 或 `deleted`，并在 `limitations` 中说明资料缺口。

目录计数和当前页必须复用同一基础集合与状态定义。`focusedConversationCount` 只统计当前 user 在 `mochat_go_work_message_focus` 中的 `to_user_type=1` 记录。

  "mode": "direct",

    "id": "msg:archive-31",
    "conversationId": "9:1:2001",
    "employeeId": 9,
    "employeeName": "张伟",

```

`mode=direct` 只返回 `to_user_type=1` 且 `to_user_id=customerId` 的员工—客户会话。`mode=group` 先验证客户群成员关系，再返回 `to_user_type=2` 的员工—群会话，并额外返回 `membershipStatus: active | left`。两种模式都必须先按稳定 `conversationId` 聚合，再从同一聚合集合计算 `total`、排序和分页。

客户存在但当前模式没有归档会话时返回空页。客户不在权限范围、客户与群无关系或只在其他员工范围可见时统一返回 404。

### 7.3 客户会话详情

新增：

```http
GET /dashboard/workMessage/customerDetail
  ?customerId=2001&conversationId=9:1:2001
  &keyword=&messageTypes=image&date=2026-08-16&pageSize=50&before=
```

响应：

```json
{
  "conversationId": "9:1:2001",
  "customerId": 2001,
  "customerName": "陈晓明",
  "employeeId": 9,
  "employeeName": "张伟",
  "targetType": "customer",
  "targetId": 2001,
  "targetName": "陈晓明",
  "focused": true,
  "stats": {
    "communicationDays": 2,
    "messageTotal": 15,
    "inboundTotal": 5,
    "outboundTotal": 10
  },
  "messages": [],
  "nextBefore": "opaque-cursor",
  "hasMore": true,
  "capabilities": []

```

直接会话必须验证 `conversationId` 的客户 ID 与 `customerId` 相同。群会话必须验证客户与群的当前或历史成员关系，并验证员工属于当前数据范围。详情统计按未筛选的完整会话计算；消息列表应用关键词、类型、日期和游标筛选。

存储层复用员工会话已有的消息集合、统计、类型过滤和游标算法，但暴露独立客户接口和客户关联校验，避免改变员工会话合同。消息游标由后端编码，前端不得解析。

### 7.4 重点关注

继续使用：

```http
PUT    /dashboard/workMessage/focus
DELETE /dashboard/workMessage/focus
```

请求体仍为 `{ "conversationId": "9:1:2001" }`。成功后刷新详情、当前关联会话卡片和客户目录关注计数。新增接口和关注资源必须加入 `dashboard.chat.v2_customer` 的页面资源目录与 RBAC 迁移；迁移只追加客户会话资源，不改变其他页面授权。

## 8. 数据来源矩阵

| 控件/数据 | 系统来源 | 当前状态 | 设计处理 |
|---|---|---|---|
| 客户主资料 | `mc_work_contact` | 已有，可能缺失或软删除 | 返回 `profileStatus`；缺失时保留归档会话并告警 |
| 有效/流失关系 | `mc_work_contact_employee` | 已有；`status=1` 有效，`status IN (2,3)` 为主动/被动删除 | 按可访问员工范围聚合，客户状态互斥计算 |
| 客户目录 | 客户主资料、关系与归档消息交集 | 当前客户会话页未接入 | 后端按客户去重、固定 50 条分页 |
| 直接会话 | 归档消息 `to_user_type=1` | 已有，但当前页以通用卡片展示 | 按 `employeeId:1:customerId` 聚合 |
| 客户所在群 | `mc_work_contact_room` + 归档消息 `to_user_type=2` | 表和群归档已有，当前页未关联 | 只显示存在成员关系且有可访问归档消息的员工—群会话 |
| 群成员状态 | `mc_work_contact_room.status/out_time/deleted_at` | 已有 | 显示“群内/已退群”，历史消息仍可读 |
| 重点关注 | `mochat_go_work_message_focus` | 已有会话级读写 | 客户目录只汇总直接会话；卡片与详情按会话展示 |
| 会话详情与统计 | 归档分表/来源注册表 | 员工工作台已有游标和统计实现 | 复用查询算法，增加客户与群关系校验 |
| 风险/超时 | `mochat_go_risk_records`、`mochat_go_timeout_records` | 表存在时可用 | 只有 capability 可用时展示；缺表不写 0 |
| 消息内容 | 归档 `msg_type/content_raw/msg_data_time/is_current_user` | 已有，部分类型字段不完整 | 类型化渲染；字段不足显示不可预览 |
| 群入站成员身份 | 当前归档字段 | 无法稳定识别 | 显式 capability 告警，不把入站消息标成选中客户 |
| 单会话下载 | 当前导出页只支持会话摘要 | 完整能力未实现 | 本页不展示下载动作 |
| 会话级 AI 摘要 | 无稳定接口与字段 | 未实现 | 本页不展示，不伪造摘要 |

## 9. 组件边界

- `CustomerConversationPage`：URL 状态、查询编排、三栏联动和跨查询缓存失效。
- `CustomerConversationDirectory`：客户模式、搜索、客户列表、固定分页和资料缺口。
- `CustomerConversationList`：客户信息、单聊/群聊、会话卡片、固定分页和关系状态。
- `CustomerConversationDetail`：标题、关注、消息筛选、完整统计、游标加载和群身份告警。
- `ConversationMessageContent`：继续负责真实归档内容类型化渲染。
- `conversation-global-api.ts`：增加客户目录、关联会话和详情类型及严格解析；无效或缺字段响应不得被当作空数据。
- 后端客户工作台处理器：参数、权限和客户关联校验。
- 后端存储层：客户目录聚合、直接/群会话聚合，以及对现有消息详情查询的内部复用。

客户页面不得读取 `EmployeeConversationPage` 的内部状态，也不得改变员工会话 URL 或交互。可以提取无状态的通用消息统计和消息流组件，但提取前后员工会话行为与测试必须保持一致。

## 10. 错误、空态与能力缺口

- 会话归档未开通：整页显示共享的“会话归档未开通”状态和现有配置入口。
- 客户目录无数据：说明当前权限范围没有可用客户归档会话，并提示检查归档、客户同步和员工范围。
- 客户资料缺失：客户项与中栏显示紧凑告警，归档会话仍可查看；不把资料缺失误报成会话不存在。
- 客户已流失：显示关系状态，但历史归档消息保持只读可查看。
- 选中客户无单聊或群聊：只在中栏显示对应空态，左栏和另一个会话页签仍可使用。
- 详情筛选无结果：保留标题和完整统计，仅消息区显示“暂无匹配消息”。
- 群成员身份缺失：右栏持续显示能力提示，发送方使用归档真实名称；没有名称时显示“群成员”，不显示选中客户名。
- 风险或超时表缺失：不显示对应数量徽标，并返回不可用 capability；不得把未接入显示成 0。
- 当前页越界：显示“当前页暂无数据”并提供回到第 1 页，不把越界当成业务空数据。
- 权限外客户、群或会话：统一 404；归档权限不足使用现有 40301；普通 RBAC 拒绝使用 403。
- 单项能力不可用时尽量保持其他两栏可操作；只有归档整体不可用或权限拒绝才阻断整页。

## 11. 查询与性能约束

- 客户目录先建立可访问员工与归档来源范围，再按客户 ID 聚合。计数、当前页和模式过滤复用同一基础查询，避免分别计算产生口径漂移。
- 关联会话查询先按稳定 `conversationId` 去重，再计算最后消息、消息总数、风险、超时和关注。禁止对每张前端卡片执行独立消息总数查询。
- 群聊关联只查询当前客户相关的 `mc_work_contact_room`，再与归档集合求交，不扫描并返回无归档的全部客户群。
- 消息详情继续使用时间、seq、分表索引和 ID 组成的不透明游标，避免大 OFFSET。
- 所有 SQL 兼容项目实际 MariaDB/MySQL 方言。若需要索引，迁移前使用真实查询计划验证，并提供安全 down migration；不为文档假定索引一定存在。
- 客户、关联会话和详情都必须在 SQL 或服务层应用同一允许员工集合，不能先返回全企业数据再由前端过滤。

### 12.1 前端自动化

- 客户目录模式、搜索、固定 50 条分页、客户选择和 URL 恢复。

- 归档未开通、403、40301、404、通用错误和重试行为。
- API 解析器拒绝缺少客户状态、关系状态、稳定会话 ID、统计或 capability 的半成功响应。

- 1600px 以上列定义为 `288px 360px minmax(560px, 1fr)`。

- 1200–1599px 客户目录为抽屉，右栏最小宽度不小于 520px。
- 768px 以下为分步单栏，返回操作可达且不丢 URL 状态。
- 卡片整行 hover/focus、选中态、分页 hover、禁用和告警对比度清晰。

### 12.3 后端与存储

- Handler：principal tenant/corp、员工权限交集、参数校验、非法模式、非法页大小、40301、403 和 404。
- 客户目录：按客户去重、模式计数、有效/流失互斥、资料缺失、关注只计直接会话、排序和分页。
- 关联会话：直接会话去重、群成员关系、已退群历史、同群多员工不丢失、总数与列表同源。
- 详情：直接客户一致性、群成员关系、完整统计、关键词/类型/日期、游标顺序和权限外 404。
- 数据库集成：真实 MariaDB 语法、归档来源选择、分表联合、空员工权限集合、跨 corp 隔离和必要查询计划。

### 12.4 浏览器验收

1. 2560×1440 下三栏填满内容区，客户目录和关联会话保持稳定宽度，右栏获得主要剩余空间。

## 13. 构建、部署与数据保护

- 实施时先运行客户页面目标测试、相关 Go 包测试、dashboard 全量测试、类型检查和生产构建。
- 页面和 API 变更优先只重建 Compose `app` 服务；不得执行 `down -v`、`down --volumes` 或删除 MySQL、Redis、应用存储卷。
- RBAC 或索引迁移必须先验证当前 schema 与已有 0141 会话工作台资源，避免覆盖用户正在进行的员工会话改动。
- 部署后检查 app、MySQL、Redis 健康状态与命名卷仍存在，再进行浏览器验收。
