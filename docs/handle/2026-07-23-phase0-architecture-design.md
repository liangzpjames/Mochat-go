# MoChat Go Phase 0 架构整理设计

> 日期：2026-07-23  
> 状态：已确认方案，待实施  
> 范围：本地开发基线、渐进式模块化单体底座、工程门禁、GitHub 仓库替换

## 1. 目标

本阶段不增加 CRM、AI 或新的营销功能。目标是把现有高完成度但复杂度集中的 Go 项目整理成可持续扩展的模块化单体，并完成可重复的本地开发、测试、Docker 验收和版本仓库基线。

Phase 0 完成后应满足：

1. 新开发者可以只依赖本地 Docker，从空环境启动、构建和验证项目。
2. 应用启动职责有明确边界，API、worker、scheduler 可以使用同一代码库按角色独立运行。
3. 新需求有统一的领域模块目录、依赖方向和测试规范，不再向三个巨型文件无边界追加逻辑。
4. 已知资源缺口、密钥缺口、风险、生产证据和后续任务均有可维护的台账。
5. `docs/handle/` 成为后续接手、规划、架构、验收和开发执行文档的统一目录。
6. 指定 GitHub 仓库的 `main` 最终只包含当前 `mochat-go/` 项目内容，同时保留覆盖前提交的可恢复引用。

## 2. 现状与约束

### 2.1 已确认现状

- 当前项目根目录是 `D:\workspace\mochat-go\mochat-go`。
- 外层 `D:\workspace\mochat-go\.git` 不包含有效 Git 仓库元数据，本地没有可复用提交历史。
- 目标远端为 `https://github.com/liangzpjames/Mochat-go.git`，当前默认分支为 `main`，覆盖前 HEAD 为 `3dcd216c188df34f2c3ed489b8e8b9473e635488`。
- 本机 PowerShell 当前找不到 `go` 命令，但 Docker 可用，因此 Phase 0 验证以 Docker 内的项目工具链为准。
- `cmd/mochat-go/main.go` 同时承担配置读取、基础设施初始化、依赖装配、HTTP 注册、worker 和 cron 启动。
- `internal/dashboard/saas_admin_page.go`、`internal/store/mysql.go`、`internal/dashboard/saas_admin.go` 已成为高风险巨型文件。
- 旧 dashboard、sidebar 和 operation 当前主要是编译产物，不能假定具有完整可维护源码。
- 生产资源、服务器、正式域名和部署密钥暂不可用，相关项目只能建立空白台账，不能伪造生产证据。

### 2.2 本阶段不做

- 不把现有单体直接改造成微服务。
- 不一次性重写或机械拆散三个巨型文件。
- 不改变现有 API 路由、数据库语义、租户隔离和异步任务行为。
- 不新增 CRM、AI、支付供应商或真实企微能力。
- 不填写不存在的服务器、密钥、域名、监控和生产验收信息。
- 不把本地 smoke 或 fake server 结果描述为真实生产证据。

## 3. 方案选择

采用“渐进式模块化单体”。

### 3.1 选择理由

- 现有测试、路由和业务资产价值高，应优先保留行为。
- 当前主要风险是复杂度继续增长，而不是功能完全缺失。
- 先隔离装配职责和规定新增代码边界，可以在低回归风险下立即改善后续开发。
- API、worker、scheduler 分角色运行可以解决未来 API 扩容重复启动 cron、长任务影响请求等问题，又不需要立即引入微服务基础设施。

### 3.2 未选择方案

- **彻底重构巨型文件**：短期影响面过大，真实生产证据尚未闭环时不适合进行高风险重写。
- **只补文档和 Git**：无法阻止复杂度继续集中，也没有形成真正的开发底座。

## 4. 目标架构

近期保持一个 Go module 和一套数据库，通过清晰模块边界形成模块化单体：

```text
cmd/mochat-go
  -> internal/app                 应用生命周期和角色装配
       -> internal/platform       共享基础设施构造与生命周期
       -> internal/modules        新领域模块
       -> 现有 internal/dashboard 兼容层，逐步迁出
       -> 现有 internal/store      兼容持久化层，逐步迁出

运行角色：
  all        = API + worker + scheduler（本地兼容默认）
  api        = HTTP/API/静态前端
  worker     = Redis 异步消费者
  scheduler  = 单实例定时调度
```

### 4.1 应用装配层

新增 `internal/app`，职责限定为：

- 解析并校验运行角色；
- 协调应用依赖的创建与关闭；
- 按运行角色启用 API、worker、scheduler；
- 为后续从 `main.go` 搬迁装配代码提供稳定入口；
- 暴露可测试的角色判断和生命周期接口。

`cmd/mochat-go/main.go` 最终只负责：

1. 读取配置；
2. 创建应用；
3. 运行应用；
4. 记录不可恢复错误并设置退出码。

Phase 0 可以采用适配器方式包裹现有装配逻辑，不要求一次性迁完所有 handler。

### 4.2 平台基础设施层

新增 `internal/platform` 作为共享技术能力的归属规则，而不是业务领域：

- MySQL、Redis 和 HTTP client 的构造；
- 进程信号、关闭顺序和资源释放；
- 日志、构建信息和运行角色；
- 后续监控、trace、Secret Manager adapter 的接入点。

现有 `mysqlconn`、`outboundhttp`、`taskrunner` 等包可继续存在。Phase 0 只建立边界和组合入口，不进行无收益的改名迁移。

### 4.3 新领域模块标准

后续新增业务领域放在 `internal/modules/<domain>/`：

```text
internal/modules/<domain>/
├── domain/          实体、值对象、状态机和纯领域规则
├── application/     用例、命令、查询和事务编排
├── ports/           repository 与外部服务接口
├── adapters/        MySQL、Redis、企微、支付、LLM 等实现
└── transport/http/  HTTP 请求解析、鉴权和响应映射
```

依赖方向：

```text
transport/adapters -> application -> domain
application -> ports
adapters -> ports
domain 不依赖 transport、adapter、数据库或外部 SDK
```

第一阶段只提供最小示例模块和编译/依赖门禁，不复制现有业务代码制造双份实现。

### 4.4 现有代码迁移策略

采用“触碰即迁移”，不做大爆炸重写：

1. 新需求必须进入对应领域模块。
2. 修改巨型文件时，优先把本次涉及的用例和持久化逻辑迁到新模块。
3. 旧 handler 可作为 transport adapter 调用新 application service。
4. 旧 `MySQLStore` 可暂时实现新模块的 repository port。
5. 每次迁移必须保持原路由和数据行为，并先补回归测试。

## 5. 工程门禁

### 5.1 架构门禁

新增可在本地和 CI 执行的检查：

- 禁止 `internal/modules/*/domain` 引用数据库、HTTP handler、外部 SDK或旧 dashboard/store 包。
- 禁止新模块反向依赖 `cmd/`。
- 记录三个巨型文件的当前字节基线；默认禁止继续增长，确需增长必须在架构例外清单说明原因、负责人和回收日期。
- 校验新增领域模块包含职责说明和测试。

### 5.2 测试门禁

验证层次：

1. 角色解析与模块边界单元测试；
2. `go test ./...`；
3. `scripts/test.sh` 快速门禁；
4. Docker 构建；
5. standalone core/saas/frontend 分组验收；
6. 视时间和资源执行 workers/cron 或完整 acceptance。

本机没有 Go 时，提供 Docker 化统一命令，确保开发者不需要预装特定 Go 工具链。

### 5.3 文档门禁

`docs/handle/README.md` 规定以下新文档统一放在 `docs/handle/`：

- 项目接手与现状分析；
- 架构设计与技术决策；
- 开发计划、阶段任务和执行记录；
- 风险、缺陷、需求和生产证据台账；
- 本地环境、测试、部署准备和验收报告。

代码旁必须紧邻的包级说明、API 契约、迁移 README 和运维脚本说明可以保留在其所属目录。

### 6.3 Git

- 获取远端旧 `main`；
- 创建带日期的远端备份分支或标签，指向覆盖前提交；
- 初始化以当前项目根目录为仓库根的本地历史；
- 排除临时输出、密钥、本地环境文件和无关外层目录；
- 将当前项目推送为远端新 `main`；
- 推送后重新读取远端引用，确认新 `main` 与本地提交一致且备份引用存在。

## 7. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 巨型装配代码拆分造成大面积回归 | Phase 0 先引入角色和组合边界，行为迁移采用小步测试驱动 |
| 本机没有 Go | 使用 Docker 内固定工具链执行测试和构建 |
| 远端覆盖不可恢复 | 覆盖前创建并验证备份引用，不删除旧对象 |
| 本地文件包含密钥或运行产物 | 提交前执行敏感文件名、环境文件和大文件审计 |
| 旧前端只有 dist | 本阶段保留产物并记录源码缺口，不直接修改压缩产物 |
| 无服务器和生产资源 | 台账留空并标注“未具备”，不伪造完成状态 |
| 全量验收耗时过长 | 先快速门禁和分组验收，记录各组耗时与失败，不隐瞒未执行项 |

## 8. 验收标准

Phase 0 只有在以下条件满足时才可标记完成：

- [ ] 架构角色及依赖边界有自动化测试。
- [ ] 默认 `all` 模式保持现有本地行为。
- [ ] `api`、`worker`、`scheduler` 的启用语义明确且可测试。
- [ ] 架构门禁能阻止新领域代码依赖旧巨型包，并阻止巨型文件无说明增长。
- [ ] Docker 内 `go test ./...` 和 `scripts/test.sh` 有新鲜执行记录。
- [ ] Docker 镜像构建成功。
- [ ] standalone 分组验收结果和耗时已记录；失败项有明确原因。
- [ ] 密钥、服务器、域名和生产资源保持空白或“未具备”状态。
- [ ] 所有 Phase 0 文档位于 `docs/handle/`。
- [ ] 远端覆盖前备份引用可读取。
- [ ] 远端 `main` 指向本地最终提交。
- [ ] 仓库中没有提交本地密钥、认证状态、临时容器数据或无关外层目录。

## 9. 后续演进顺序

Phase 0 之后按以下顺序推进：

1. 补齐真实企微、微信开放平台、双租户、生产前端和稳定性证据；
2. 在真实业务回归保护下逐块迁出巨型 handler/store；
3. 恢复或重建旧三端可维护源码；
4. 完成支付、交付和售后闭环；
5. 建设 CRM 销售闭环；
6. 最后建设可评测、可追溯、可计费的 AI 能力。
