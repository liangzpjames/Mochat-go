# Phase 3.5 产品化返工设计

## 1. 背景与结论

Phase 3.5 当前九个路由已经具备基础接口与页面骨架，但浏览器截图证明其尚未达到产品交付标准：页面直接暴露 `customer`、`contactRate`、`report` 等内部字段；缺少指标解释、趋势、详情、分页、状态反馈和跨页下钻；订单在无联系人时无法形成完整工作流；设置页仅提供任意键值写入；会话 Provider 不可用时只有单行提示。

本次采用“工作流优先、统一组件、真实数据闭环”的返工方案。圆弧只作为信息架构和业务覆盖基准，不照搬其视觉；最终页面必须沿用现有 MoChat 顶栏、侧栏、色彩、卡片、表格、间距和交互习惯。

## 2. 职责与禁止事项

- 主任务只负责设计、文档自审、代码审查、数据工作流审查和浏览器截图验收。
- 独立开发任务负责代码、测试与修复；完成后必须通知主任务。
- 本轮禁止部署、重建容器、修改 Compose、清理 Docker 或触碰数据卷。
- 验收只使用当前已运行的 `mochat-go-desktop` 服务；若代码必须部署后才能验证，主任务将其记录为待部署证据，不自行部署。
- 禁止把路由可达、HTTP 200、空表格、静态指标或测试 fixture 当作完成证据。

## 3. 统一体验模型

九页统一采用以下页面结构：

1. 页面标题区：中文标题、用途说明、数据新鲜度、限制状态和主要操作。
2. 筛选区：日期、员工、部门及业务筛选使用真实选择器；支持查询、重置和筛选摘要。
3. 摘要区：中文指标卡，包含指标值、单位、口径说明和可用时的环比/同比。
4. 主体区：按页面使用趋势图、漏斗、分布图或业务表格；禁止直接输出内部 key。
5. 明细区：分页、排序、明确列名、格式化时间/金额/状态和行级详情入口。
6. 状态区：分别处理加载、无数据、失败、无权限、数据受限和 Provider 缺失。
7. 反馈区：写操作必须显示处理中、成功或服务端错误，并在成功后回读。

共享组件放在 `web/apps/dashboard/src/features/phase35/components/`，共享字典与格式化放在 `features/phase35/presentation/`。页面不得各自复制指标、空态、错误态和表格实现。

## 4. 页面设计

### 4.1 好友 `/customer/friends`

- 指标：好友总数、今日新增、已分配、未分配、已打标签。
- 筛选：关键词、负责人、标签、添加日期、分配状态。
- 列表：姓名/备注、手机号脱敏、负责人、标签、来源、添加时间、更新时间。
- 详情抽屉：基础资料、负责人、标签、来源、关联线索/联系人/商机/订单。
- 工作流：筛选 → 打开详情 → 跳转关联订单或客户记录 → 返回后保持筛选。

### 4.2 客户群 `/customer/group`

- 指标：群总数、活跃群、成员总数、今日新增成员。
- 筛选：群名称、群主、群状态、创建日期。
- 列表：群名称、群主、成员数、活跃状态、创建和更新时间。
- 详情抽屉：群资料、群主、成员分页、成员角色与入群时间。

### 4.3 订单 `/customer/order`

- 指标：订单数、成交金额、待处理、已完成、已取消。
- 联系人使用可搜索选择器，不要求用户输入内部 ID。
- 创建表单：联系人、关联商机、金额、币种、订单标题、备注；校验错误就地展示。
- 列表：订单号、联系人、商机、金额、状态、创建人、创建时间、更新时间。
- 详情抽屉：订单信息、状态时间线、审计记录；允许的状态流转由服务端决定。
- 工作流：选择验收联系人 → 创建订单 → 列表出现 → 打开详情 → 状态变更 → 报表刷新并可下钻到该订单。

### 4.4 客户设置 `/customer/settings`

- 使用明确的设置分类和字段定义，不再暴露任意 key/value 作为主要界面。
- 至少覆盖客户来源、阶段、默认分配或本阶段真实支持的配置类型。
- 展示字段说明、当前值、启用状态、版本、更新时间和更新人。
- 保存前校验；保存后回读；冲突显示版本提示；审计事件可在行为报表查看。

### 4.5 客户分析 `/data/customer`

- 指标：期初客户、新增、留存、流失、净增长；无法计算的指标显示口径限制。
- 趋势：新增/流失/净增长按日或周。
- 分布：来源、负责人或标签，仅展示真实可用维度。
- 明细：可从指标或趋势点下钻至客户清单。

### 4.6 会话分析 `/data/employee`

- Provider 可用时展示会话数、员工消息、客户消息、活跃员工、响应指标和员工排行。
- Provider 不可用时展示结构化受限卡：缺失能力、受影响指标、恢复条件；不得显示伪造的 0。
- 仍可展示不依赖 Provider 的真实组织范围和数据截止时间。

### 4.7 转化分析 `/data/conversion`

- 漏斗：线索 → 联系人 → 商机 → 赢单 → 订单。
- 每阶段显示对象数、相对上一阶段转化率和口径说明。
- 支持按员工、部门和日期筛选；点击阶段进入对应明细。
- 新建验收订单后，订单阶段和综合报表必须按同一口径更新。

### 4.8 行为分析 `/data/behavior`

- 指标：行为总数、涉及对象数、涉及操作者数、主要行为类型。
- 筛选：行为类型、操作者、对象类型、日期。
- 趋势与分布使用中文行为字典；事件表展示对象、操作者、发生时间和详情。
- 设置更新必须可查到对应审计事件并能查看变更摘要。

### 4.9 综合报表 `/data/report`

- 汇总客户、转化、订单和行为核心指标。
- 包含客户趋势、转化漏斗、订单状态/金额、行为分布和受限能力说明。
- 所有卡片和图表均可追溯到明细或对应业务页。
- 不重复实现统计 SQL，复用其他报表的统一口径。

## 5. 验收数据设计

- 允许创建小规模验收数据，统一使用 `P35-ACCEPT-` 名称/业务键前缀。
- 数据集至少包含 2 个联系人、1 条线索、1 个商机、2 个订单、2 项设置与相应审计事件；客户群仅在现有 Provider 支持安全创建时加入。
- 验收数据必须 tenant/corp 隔离，能通过正常 API 或 UI 创建；禁止直接伪造前端结果。
- 提供只删除 `P35-ACCEPT-` 数据的清理命令或脚本，但本轮开发与审核不执行 Docker 或数据卷清理。
- 截图、报告及临时证据全部输出到 D 盘，不在 C 盘建立构建缓存。

## 6. 数据与权限门禁

- 所有查询同时限制 tenant、corp 和当前用户数据范围。
- 员工/部门筛选与授权范围取交集；列表与详情使用同一范围。
- 日期使用租户时区与半开区间 `[startAt, endAt)`。
- 金额以整数最小货币单位存储，页面格式化显示。
- 转化率分母为 0 时返回 `null`，页面显示 `--` 和说明，不显示错误百分比。
- Provider 缺失通过结构化 `limitations` 返回，不得以全 0 冒充真实数据。
- 写操作包含权限、校验、幂等/版本控制和审计。

## 7. 审核门禁

每页必须同时满足：

- 圆弧基准的业务覆盖清单已映射；视觉无需照搬。
- 与现有 MoChat 页面风格统一，1280×720 下无异常裁切、拥挤或大面积无意义空白。
- 中文业务文案完整，无内部字段名直接暴露。
- 加载、空、错误、无权和受限状态均有测试。
- 至少一个主要工作流通过真实 API/UI 完成并回读。
- 自动化测试、typecheck、Phase 3.5 gate 和 `git diff --check` 通过。
- 主任务逐页查看截图和 DOM；任何一项不满足即退回开发任务。

## 8. 完成定义

只有九页均通过代码审查、数据合同审查、真实工作流审查和逐页截图审查，且问题全部由开发任务修正后，Phase 3.5 产品化返工才能结束。主任务不会部署，也不会因开发任务声称完成而直接通过。
