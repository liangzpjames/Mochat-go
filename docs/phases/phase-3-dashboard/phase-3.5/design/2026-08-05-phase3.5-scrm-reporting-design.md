# Phase 3.5 SCRM 扩展与数据报表设计

## 1. 目标与范围

Phase 3.5 交付 9 个可真实查询、可验证数据来源的页面：

| 业务域 | 路由 | 核心闭环 |
| --- | --- | --- |
| SCRM | `/customer/friends` | 同步状态、筛选、详情、标签与负责人信息 |
| SCRM | `/customer/group` | 群筛选、成员与群主详情、群统计 |
| SCRM | `/customer/order` | 创建/查询订单、关联客户与商机、状态流转 |
| SCRM | `/customer/settings` | 字段、来源、阶段与分配规则的读取和维护 |
| 报表 | `/data/customer` | 客户新增、存量、流失、结构、趋势和明细 |
| 报表 | `/data/employee` | 员工会话量、响应、排名和明细；无会话存档时明确受限 |
| 报表 | `/data/conversion` | 线索到联系人、商机、订单的漏斗与下钻 |
| 报表 | `/data/behavior` | 现有业务事件的趋势、分布与明细，不虚构事件仓 |
| 报表 | `/data/report` | 统一选择报表、组织/员工/日期筛选、汇总、趋势和明细 |

不提前实现 Phase 3.6 的 AI 与企业设置，不以 fixture、demo、静态成功提示或仅可访问路由作为完成证据。

## 2. 方案选择

采用“统一 Phase 3.5 查询合同 + 复用现有业务表和 Provider”的渐进方案。后端在 tenant、corp 和数据权限边界内聚合 `mc_work_contact`、客户群/成员、现有 SCRM 线索/联系人/商机、会话归档、营销来源及新增订单/配置表；React 页面只消费稳定合同，不拼接多套 legacy 响应。

未采用逐页直连历史 API，因为会把字段差异、分页和权限语义泄漏到 UI；未采用独立数据仓，因为本阶段应优先利用现有实时业务数据，且当前范围不需要引入新的基础设施。

## 3. 数据与指标合同

所有报表请求必须包含 tenant、corp、租户时区、开始/结束日期及可选部门/员工筛选。服务端统一返回 `summary`、`series`、`dimensions`、`items`、`pagination`、`freshness` 和 `limitations`。

- 事件时间使用业务发生时间；缺失时才使用创建时间，并在 `limitations` 声明。
- 日界线使用租户时区；API 使用半开区间 `[startAt, endAt)`。
- 客户按 corp 内 `external_userid` 或可验证联系人主键去重，禁止姓名匹配。
- 转化率分母为上一阶段进入数，分子为在窗口内首次进入下一阶段的去重对象数；分母为 0 时返回 `null`。
- 迟到事件按查询时实时重算；`freshness` 返回数据截至时间及 Provider 状态。
- 会话、行为或外部订单 Provider 不可用时返回可解释的 `limitations`，页面展示受限状态，不生成假数据。

## 4. 组件与数据流

后端新增聚焦的 Phase 3.5 模块或在现有 SCRM 模块中增加明确边界：好友/群适配器、订单与设置领域服务、指标字典、报表查询服务及 HTTP handler。数据访问层必须复用已有 store 能力；只有无法表达稳定领域关系时才新增 migration。

前端建立 `features/phase35`，共享筛选栏、指标卡、趋势图、维度分布、明细表、限制说明和刷新状态。九个路由各有页面入口和测试，但共享 API client 与 report primitives。

数据流：浏览器筛选条件 → Dashboard API → 认证与 RBAC → tenant/corp/组织范围 → 现有业务表或 Provider → 统一合同 → 汇总/趋势/明细一致渲染。写操作必须具备权限、校验、事务/幂等与审计，并在刷新后可读回。

## 5. 交付批次

1. 基线与复用审计：九页档案、指标字典、现有表/API/Provider 映射、完成门禁。
2. SCRM 扩展：好友、客户群、订单、客户设置。
3. 客户与转化报表：客户分析、转化分析，优先复用已完成的 SCRM 主链。
4. 会话、行为与综合报表：对 Provider 缺口显示真实限制，完成全阶段回归与证据。

## 6. 错误、权限与安全

统一区分 400/401/403/404/409/422/500；加载、空、错误、无权限和 Provider 受限状态均可见。列表与详情采用相同数据范围。所有 SQL 同时限制 tenant 和 corp，员工/部门筛选与当前用户数据范围取交集。导出若无现有安全能力则不在本阶段伪造。

## 7. 验收

- Go 单元/集成测试、Dashboard Vitest/typecheck/build、manifest gate 全部通过。
- 九页均不是 demo/placeholder；导航、直接 URL、刷新和前进后退正常。
- 至少验证一条跨页面真实链路：SCRM 客户/商机/订单数据可进入客户或转化报表，并能下钻回明细。
- Docker 仅沿用 compose project `mochat-go-desktop`；禁止 `down -v`、`volume rm`、更换 project name 或创建替代数据卷。部署前后记录 volume 名称与挂载目标并比较一致。
- 浏览器逐页检查真实数据、空/错误/受限状态和关键交互；截图保存到 `D:\workspace\mochat-go\output\phase35-browser-20260805`，最终报告引用证据。

## 8. 完成定义

只有九页功能、数据合同、权限/持久化、自动化测试、Docker 健康、真实工作流和截图证据全部闭合，才能声明 Phase 3.5 完成。外部 Provider 缺失造成的功能缺口必须列为遗留项；页面可访问不等于阶段完成。
