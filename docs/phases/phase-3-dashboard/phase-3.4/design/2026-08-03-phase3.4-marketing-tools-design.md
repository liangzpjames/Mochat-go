# Phase 3.4 营销工具设计

日期：2026-08-03

状态：待实施

参考基线：Phase 3.3 纵向业务闭环、圆弧 AI 当前在线界面

## 1. 设计结论

Phase 3.4 固定覆盖 `web/apps/dashboard/src/benchmark/manifest.json` 中“营销工具”分组的 9 个页面：

| 页面 | 路由 | 圆弧已观察主界面 |
| --- | --- | --- |
| 渠道活码 | `/acquisition/v2-channel-code` | 名称、创建人、使用人员筛选；二维码、标签、有效期、新增好友数和操作列表 |
| 群活码 | `/acquisition/group-code` | 名称、日期筛选；二维码、类型、扫码次数、关联活码和明细列表 |
| 获客链接 | `/acquisition/redirect-link` | 授权状态与“立即授权并使用”入口 |
| 微信客服 | `/acquisition/wechat-customer-service` | 名称筛选；客服账号、接待员工、接待方式和操作列表 |
| 活码短链 | `/acquisition/live-code-short-chain` | 名称、日期筛选；短链、状态、形式、创建人和操作列表 |
| 一键加群 | `/acquisition/group-template` | 名称筛选；模板状态、拉群总数、今日新增群聊和操作列表 |
| 精准群发 | `/acquisition/precise-group-send` | 客户群发/群聊群发标签页；日期筛选、内容、执行结果和执行数据列表 |
| 朋友圈 | `/acquisition/friends-circle` | 朋友圈/朋友圈素材标签页；任务名称、日期、发送方式、状态和完成情况列表 |
| 素材管理 | `/acquisition/material-management` | 公共/部门/个人素材及聊天侧边栏配置；文件筛选、添加素材、批量操作和素材列表 |

目标不是只复刻列表外观，而是在保留圆弧信息架构和主要操作入口的同时，为每个页面提供至少一条真实查询或命令主流程。无法安全接入的企业微信能力必须显示真实授权或 Provider 状态，不得以 fixture、假链接或伪成功替代。

## 2. 方案选择

采用“四批纵向闭环”，不采用一次性铺完 9 个页面，也不采用只做视觉的演示版本。

1. **渠道获客**：渠道活码、群活码、活码短链。
2. **接待转化**：获客链接、微信客服、一键加群。
3. **内容触达**：精准群发、朋友圈。
4. **素材底座与收尾**：素材管理、跨页面素材选择、全量验收。

每批均按页面档案、旧能力审计、失败测试、后端合同、React 页面、浏览器主流程和证据更新的顺序交付。批次可以独立构建、回滚和验收；后续批次只依赖已经提交的接口合同，不依赖对话上下文。

## 3. 旧能力复用边界

现有 Go standalone 已具备较完整的旧 Dashboard 能力，实施前优先建立稳定 adapter，不重复创建同义接口：

| 新页面能力 | 优先复用能力 | 决策 |
| --- | --- | --- |
| 渠道活码 | `/dashboard/channelCode/*`、`channelCodeGroup/*`、现有 MySQL store 和企业微信 contact-way provider | 保留业务与存储逻辑，重做 React 视图和新页面 adapter |
| 群活码 | `workRoomAutoPull/*`、`roomTagPull/*` 的群二维码、群选择、扫码入群和统计能力 | 审计语义后组合 adapter；不把标签建群任务直接冒充通用群活码 |
| 一键加群 | `workRoomAutoPull/*` | 复用模板、群容量与备用群切换逻辑，补圆弧页面合同 |
| 精准群发 | `contactMessageBatchSend/*`、`roomMessageBatchSend/*` | 分别承接客户群发和群聊群发标签页；测试环境保持防误发门禁 |
| 素材管理 | `mediumGroup/*`、现有上传与存储账本 | 建立统一素材查询、上传、分组、移动和删除 adapter |
| 活码短链 | 渠道码、对象存储和审计能力 | 新增短链领域合同；不得直接暴露原始对象地址或无审计跳转 |
| 获客链接 | 企业授权、外部联系人配置和回调能力 | 授权先行；未授权时只展示状态和授权入口 |
| 微信客服 | 企业微信客服 Provider（若当前环境已配置） | Provider 隔离；缺失时明确阻断创建与同步 |
| 朋友圈 | 企业微信朋友圈 Provider 与异步任务（若可用） | 先审计再接入；自动化环境禁止真实发布 |

复用旧 handler 时，前端不直接解析多种旧响应；Phase 3.4 feature adapter 统一分页、错误、权限和状态字段。旧 URL 仅保留兼容入口，不维护双套产品视图。

## 4. 前端结构与页面合同

在 `web/apps/dashboard/src/features/phase34/` 下按批次拆分模块，共用轻量营销工作台组件，不建立包含 9 页全部逻辑的单文件：

- `marketing-page-shell`：标题、说明、授权/Provider 状态、刷新和错误边界；
- `marketing-filter-bar`：关键词、创建人、日期、状态和 URL 查询参数同步；
- `marketing-table`：分页、空数据、筛选无结果、行操作和批量选择；
- `marketing-task-state`：异步任务的排队、执行、部分失败、重试和取消；
- 各批次独立 page、API adapter、类型和测试文件。

页面视觉遵循当前 Dashboard shell，并参考圆弧的白底内容区、紧凑筛选栏、主操作按钮、表格、标签页、抽屉和弹窗。验收重点为功能覆盖、信息层级和操作反馈，不要求所有像素与圆弧完全一致。

列表页的关键词、状态、日期、标签页和分页写入 URL。写操作成功后只失效对应页面或资源缓存。详情、编辑、统计和执行结果优先使用抽屉或独立详情视图；浏览器刷新、前进和后退必须恢复筛选与标签页。

## 5. 后端与数据流

统一数据流：

```text
页面交互
→ Phase 3.4 React API adapter
→ 认证、租户、企业和动作权限校验
→ 营销 application service
→ MySQL repository / 企业微信 Provider / 异步任务
→ 审计与用量账本
→ 查询刷新并验证持久化结果
```

服务端只从认证上下文解析 `tenant_id`、`corp_id`、操作者和数据范围，不信任客户端提交的租户、企业或员工权限范围。营销资源至少包含租户、企业、创建人、版本、状态和时间字段；可变配置使用版本控制，重试命令使用稳定幂等键。

企业微信写操作必须通过 Provider，并具备超时、重试、幂等和部分失败语义。精准群发、朋友圈发布、批量同步和短链统计聚合进入任务中心。自动化测试只使用隔离 Provider，禁止真实发送消息、发布朋友圈或修改生产授权。

## 6. 状态与错误语义

| 对象 | 状态规则 |
| --- | --- |
| 活码/短链 | `draft` → `active` → `disabled` / `expired`；删除采用可审计停用或软删除 |
| 授权资源 | `unauthorized` → `authorizing` → `authorized` / `failed` / `expired` |
| 群发/朋友圈任务 | `draft` → `scheduled` / `queued` → `running` → `partially_succeeded` / `succeeded` / `failed` / `cancelled` |
| 素材 | `processing` → `available` / `failed` / `disabled`；删除前检查引用关系 |

统一错误语义：参数无效 `400`，无权访问 `403`，不存在或隐藏资源 `404`，版本或重复提交冲突 `409`，非法状态流转 `422`，Provider 暂不可用 `503`。页面覆盖首次加载、空数据、筛选无结果、权限不足、未授权、网络异常、可重试失败、重复提交、异步进行中和登录失效。

## 7. 四个实施批次

### 批次 1：渠道获客

渠道活码先复用现有完整读写链路，完成列表、分组、创建/编辑、停用、客户明细和统计。群活码完成列表、创建、关联二维码、扫码统计和详情；复用能力不匹配时新增独立合同。活码短链完成创建、启停、复制、跳转解析和访问统计，跳转必须记录安全审计并限制目标协议。

### 批次 2：接待转化

获客链接以企业授权状态为前置，完成授权、链接创建/停用和转化查询。微信客服完成账号同步、接待员工配置、接待方式和状态查询。一键加群复用自动拉群能力，完成模板、群序列、容量切换、启停和统计；备用群切换需要并发测试。

### 批次 3：内容触达

精准群发的两个标签页分别接入客户群发和群聊群发，覆盖草稿、目标筛选、内容预览、创建任务、执行结果、失败明细和提醒。朋友圈覆盖任务和素材标签页；若 Provider 尚未具备正式发布能力，允许先完成真实草稿、审批和 Provider 阻断状态，但不得把页面标记为 Phase 3.4 完成。

### 批次 4：素材底座与阶段收尾

素材管理覆盖公共、部门、个人素材及聊天侧边栏配置，完成上传、处理状态、分组、移动、批量操作、引用检查和删除。统一素材选择合同供活码、群发和朋友圈复用。最后执行 9 页全量回归、双租户/双企业/多角色隔离、Docker 构建与部署、截图和 manifest 升级。

## 8. 测试与验收

每批先建立失败测试，再实现最小纵向闭环。至少覆盖：

- Go 领域/application 单元测试；
- repository 合同和 MariaDB 集成测试；
- HTTP handler 的权限、错误和响应合同测试；
- React adapter 和页面交互测试；
- 双租户、双企业、多角色隔离；
- 适用的幂等、并发、重试、部分失败和执行计划测试；
- TypeScript、lint、Vitest、Go、架构边界和生产构建；
- `1440x1000` 浏览器主流程和截图证据。

浏览器验收必须完成“登录 → 进入页面 → 查询或写入 → 验证反馈 → 刷新并复核持久化 → 更换企业或角色验证隔离”。只看到按钮、表格或成功提示不能替代业务结果验证。

## 9. Manifest 与完成定义

9 个页面只有在全部门禁通过后才能改为 `implementation=native` 或经审查批准的 `legacy-adapter`、`backend=ready`、`acceptance=e2e-passed`，并补齐设计、验收和截图证据。

Phase 3.4 完成必须同时满足：

- 9 个页面均不再使用 `DemoPage`、`PlaceholderPage` 或生产 fixture；
- 每页至少一条真实查询或命令主流程；
- 写操作具备持久化、权限、审计、异常和刷新复核；
- 外部能力具有正式 Provider 或明确的未完成记录，未接入页面不得伪装完成；
- 页面、接口、隔离、浏览器、构建和 Docker 门禁全部通过；
- 阶段报告明确记录命令、结果、证据和遗留风险。

## 10. 明确不纳入

- 不扩展 Phase 3.5 的 SCRM 与数据报表页面；
- 不实现 Phase 3.6 的 AI 设置和企业设置；
- 不复制圆弧源码、访问令牌、真实客户数据或私有素材；
- 不在自动化环境执行真实群发、朋友圈发布或不可逆授权操作；
- 不用视觉相似、静态 fixture、无结果按钮或旧页面可访问代替 Phase 3.4 完成。
