# Phase 2 前端逐页迁移设计

> 日期：2026-07-28  
> 状态：设计修订完成，实施中

## 目标与边界

Phase 2 将 Dashboard、Sidebar 和 Operation 从 legacy 前端逐页迁移到统一 React 技术栈，同时保持现有 URL、权限语义和业务可回滚。SaaS Admin 已是独立 React 应用，本阶段只维护跨应用入口和发布一致性，不重复迁移。

本阶段不以“新页面数量”替代完成度。只有页面元数据、自动化验证、视觉证据、manifest 切换和回滚记录同时闭环，单条路由才计为完成。

## 实施顺序

### 1. 建立不可被刷新覆盖的元数据基线

- 单人开发不维护 `owner`；页面清单、override、阻塞报告和校验均删除负责人字段。
- 将工具生成的页面事实与人工维护的 `risk`、`batch`、许可证结论分离。
- audit refresh 只更新生成字段，通过 override 合并人工字段。
- 先写防覆盖测试，再实现合并逻辑。
- 为当前 134 条未基线化页面建立风险和候选批次；未完成前不计算阶段百分比。

### 2. Dashboard Batch 2：基础列表与 CRUD

- 优先选择依赖少、无富文本/图表/上传、API 契约明确的页面。
- 每条路由独立完成 API contract、组件测试、可访问性检查、视觉对比和 Playwright。
- 验收通过后仅切换该路由 manifest；出现回归时单路由回退 legacy。
- 页面级动态导入是硬门禁，避免 Dashboard 首包继续增长。

### 3. Dashboard Batch 3：资源密集页面

- 覆盖上传、富文本、图表、二维码等能力。
- 引入资产或依赖前必须有来源与许可证证据。
- 大型依赖必须页面级懒加载，并记录构建体积变化。

### 4. Dashboard Batch 4：复杂业务流程

- 覆盖营销、异步任务、跨页状态和外部平台联动。
- 需要真实企微/微信开放平台或真实租户的页面，在外部证据可用前保持 legacy。
- 采用端到端业务场景验收，不以静态页面渲染作为完成依据。

### 5. Sidebar 与 Operation

- Dashboard 模式稳定后建立 Sidebar React app，共享认证、API client、权限和错误语义。
- Sidebar 验收后复用同一模式迁移 Operation。
- 两者保持独立构建入口和端口，避免与 Dashboard bundle 耦合。

### 6. legacy 退出

- manifest 中 legacy 路由降为零后进入观察期。
- 观察期内验证历史书签、深链、query/hash、权限拒绝和 API 非 SPA 回退。
- 观察通过后另立任务删除旧运行引用、依赖和构建产物；删除操作不得与最后一批页面切换混在同一提交。

## 单路由交付门禁

每条迁移路由必须同时满足：

1. API 请求、响应、业务错误和权限契约有自动化测试。
2. 加载、空态、错误态、只读态和主要写操作有组件测试。
3. 与 legacy 页面完成桌面和移动端视觉对照，差异有明确决定。
4. Playwright 覆盖真实 Go 静态路由层和关键用户流程。
5. manifest 仅切换目标路由，回滚方式已验证。
6. Docker 中应用身份、深链和静态资源返回正确。
7. 页面采用动态导入，构建体积变化有记录。

## 批次治理

页面按业务域分组，但发布批次由风险和依赖决定。`risk` 决定测试深度，`batch` 决定候选顺序。生成审计数据不得覆盖决策字段；未基线化项目始终作为阻塞显示。

阶段进度使用“满足全部门禁的已迁移路由数 / 已基线化目标路由数”。在 134 条页面完成元数据基线前，不发布百分比。

## 默认决策原则

不需要产品取舍时，由实施方直接采用以下最佳建议，不逐项请求确认：

- `low`：只读或简单表单、依赖少、API 契约完整、无上传/富文本/图表/外部平台联动，优先进入 Dashboard Batch 2。
- `medium`：常规 CRUD、权限动作较多或存在多个关联接口，仍可进入 Dashboard Batch 2，但需要完整组件测试与写路径 Playwright。
- `high`：上传、富文本、图表、二维码、大型依赖、跨页状态或异步任务，进入 Dashboard Batch 3 或 Batch 4。
- `critical`：真实企微、微信开放平台、真实租户副作用、不可逆写操作或缺少可验证回滚路径，保持 legacy，直到真实证据可用。
- `batch` 先按应用边界分为 `dashboard-batch2`、`dashboard-batch3`、`dashboard-batch4`、`sidebar`、`operation`、`blocked-external`；同批内部按依赖数量、契约完整度和回滚成本排序。

只有以下情况需要开发者决定：

- 业务语义在 legacy 行为、Go API 和文档之间互相冲突。
- 必须接受可见功能差异或删除现有能力。
- 需要真实账号、租户、凭据、许可证结论或不可逆外部操作。
- 迁移会改变既有 URL、权限模型、数据写入语义或回滚边界。

## 关键风险与对策

- 视觉回退：保留 legacy 截图基线，差异必须显式接受。
- 权限漂移：导航可见性与服务端路由授权使用同一 access 数据，并分别测试。
- 发布串包：持续比较 Dashboard、SaaS Admin、Sidebar、Operation 的 HTML 身份与资源前缀。
- bundle 膨胀：页面级动态导入与体积记录设为合并门禁。
- 外部依赖不可测：保持 legacy，不用 mock 证据替代真实平台验收。
- 元数据丢失：生成事实与人工 override 分层，使用防覆盖回归测试。

## 第一实施任务

修订 page metadata schema，删除 `owner` 维护与负责人阻塞逻辑；随后为 134 条未基线化页面生成 `risk` 与 `batch` 建议，并确定 Dashboard Batch 2 的第一组路由和可计算基线。
